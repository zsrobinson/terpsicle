# Terpsicle v2: technical plan

The plan every v2 agent builds from. It turns the owner's decisions of 2026-09-26 into names, tables, routes and an order of work, so agents working in parallel converge on the same contracts.

**Precedence.** The owner's decisions win, then this document, then the older docs. Where `SPEC.md`, `DESIGN.md`, `BUILD.md`, `DATA.md` or `ANALYTICS.md` still say otherwise, this document wins and the implementing PR fixes the older doc. Once a table or schema lands in code, the code wins (`DATA.md`'s rule) and the PR updates this document too. Anything not decided here: pick the simplest option consistent with this file, `DESIGN.md` §5 and `SPEC.md` §3.13, and state the interpretation in the PR.

**Out of scope.** Earshot and Orgs are on the back burner. Don't build them, and don't add their code paths, tables, routes, bindings or flags. The research drafts' Earshot parts (anonymous credentials, pseudonyms, the `earshot` Worker, the `Campus` object) are shelved with them.

Three products, one origin (`terpsicle.com`), one TanStack Start app, one Worker, one web app manifest, one service worker at root scope, one push subscription per device and one session cookie.

## 2. Routing rules for `/`

1. **The installed PWA** starts at `start_url: "/schedule"`, so it never sees `/`.
2. **A session goes straight to `/schedule`.** The Worker handles `GET /` before the app: if the request has a `__Host-session` cookie (presence only, no D1 lookup), it answers `302 Location: /schedule`. An expired cookie costs one extra hop, nothing worse.
3. **Saved local data goes straight to `/schedule`.** Local data lives in IndexedDB, which only the browser can read:
   - the scheduler sets `localStorage["terpsicle:returning"] = "1"` whenever the plans store holds at least one plan (and clears it after "Sign out and remove plans from this device");
   - a tiny inline head script on `/` checks that key synchronously, before first paint, and calls `location.replace("/schedule" + location.search)`;
   - if the key is missing (storage cleared, or data from before this change), the same head script counts plans in IndexedDB directly (`plans.count() > 0`; no Dexie on `/`), sets the flag again and replaces then. The marketing content renders hidden until that check finishes, at most 150 ms, so returning visitors don't see a flash. When the router navigates to `/` from another page, the route's `beforeLoad` applies the same check.
4. **Everyone else sees the marketing page.**
5. **`/?stay`** always shows the marketing page, so "About Terpsicle" in the product menu can link to it without bouncing.

The rule lives in `src/features/marketing/returning.ts` (a pure `shouldSkipMarketing({hasSessionCookie, returningFlag, planCount})` in `src/core/routing` so it's testable; the head script inlines it) and `src/server/routing.ts` for the cookie hop. Both redirects keep the query string. The placeholder page is engineering's; the brand and marketing track (the owner's prototype track) designs the real one. The placeholder states the three products in plain words with one primary button, "Open the scheduler", and links to Reviews and Chat.

### 3.2 Service worker (`/sw.js`, `src/server/service-worker.ts`)

One service worker at scope `/`. It keeps today's rules (STATUS.md, "Service worker") and adds push. Bump `SERVICE_WORKER_VERSION` to 2.

| Requests | Strategy |
|---|---|
| Navigations under `/schedule`, `/reviews`, `/chat`, `/settings`, `/admin`, `/signin`, `/privacy`, `/` | Network-first. On network failure, the cached copy of that path, else the most recently cached page (every path serves the same SPA shell). |
| Navigations to `/api/*` (sign-in) and `/auth/*` (test mode) | Network only, never cached, never a fallback. |
| `/assets/*` | Cache-first as fetched, capped at 400 files (as today). |
| Other requests to `/api/*` (including the WebSocket), `/data/*`, `/ingest/*`, `/avatars/*`, `/auth/*` | Pass through. `/api` answers are per person and must never be cached. |

Push handlers, in the same file:
- `push`: parse `PushPayloadSchema` (`{v: 1, type, title, body, url, tag}`, §6.3) and always call `showNotification(title, {body, tag, data: {url}, icon: "/icons/icon-192.png", badge: "/icons/badge-72.png"})`. A push that shows nothing gets the subscription revoked by Safari and counts against us in Chrome, so an invalid payload still shows "Terpsicle: open the app for details".
- `notificationclick`: close it, then focus an open window and navigate it to `data.url`, or `clients.openWindow(data.url)`. Only same-origin paths starting with `/` are opened.
- `pushsubscriptionchange`: re-subscribe with the VAPID public key and `POST /api/push/subscribe` (same-origin `fetch` from the service worker carries the session cookie).

Registration stays production-only, plus `localhost` when `VITE_SW_DEV=1` for push work. Previews don't register it.

### 3.3 Push subscription

- **One per device.** The browser has one subscription per service worker registration, and `push_subscriptions.endpoint` is unique. Subscribing upserts by endpoint, so if a second account signs in on the same device the row moves to that account and the first account's notifications stop reaching it. Signing out deletes the device's row (the sign-out request carries the endpoint).
- **Asking for permission** happens only on a person's own tap: a channel toggle in `/settings/notifications`, turning on a seat alert, or "Turn on notifications" in the chat list. Never on load.
- **iOS** allows web push only for a Home Screen app (iOS 16.4+). In a Safari tab the toggle shows "On iPhone, add Terpsicle to your Home Screen first: Share, then Add to Home Screen." with an "Add to Home Screen" link that opens the install dialog (§3.4).

### 3.4 The install prompt (`src/features/pwa/`)

A dialog after key moments that explains the benefits. It's allowed by the owner's decision; it isn't a confirmation dialog, and it's never a banner.

- **Triggers** (`requestInstallPrompt(trigger)`):
  - `first-sign-in`: after the first successful sign-in on this device;
  - `chat-joined`: the first time you open one of your chat rooms;
  - `alert-on`: the first time you turn on a seat alert.
- **Never shown when:**
  - already installed: `matchMedia("(display-mode: standalone)").matches` or `navigator.standalone`;
  - the platform can't install: no `beforeinstallprompt` captured on Chromium, and not iOS/iPadOS Safari (Firefox desktop, for example);
  - it was shown earlier in this session;
  - it was dismissed less than **90 days** ago, or twice in total (then never again, except from the menu item below).
- **Content:** title "Put Terpsicle on your home screen", then three lines: "Get notified when a seat opens or a classmate replies", "Open it from your home screen, like an app", "Use the full screen, without browser bars". Buttons: **Install** and **Not now**.
  - **Android and desktop Chromium:** `beforeinstallprompt` is captured at startup (`preventDefault()`, kept), and **Install** calls its `prompt()`.
  - **iOS and iPadOS Safari:** the dialog shows the steps instead of an Install button: 1 tap Share (with the icon), 2 "Add to Home Screen", 3 open Terpsicle from your Home Screen. One button: **Got it**.
- **Always available, quietly:** "Install app" in the account menu and in `/settings/notifications`, which opens the same dialog regardless of cooldown.
- **State:** `localStorage["terpsicle:install-prompt"]` = `{dismissals, lastDismissedAt}`, read with try/catch and a zod schema; storage failures mean "don't show".
- `appinstalled` → the analytics event `pwa_installed`.

## 4. Identity

### 4.1 Rules
- **Sign in with Google only.** No magic-link fallback, no passwords, no other providers.
- **UMD accounts only:** the ID token's `hd` must be exactly `terpmail.umd.edu` or `umd.edu`, and `email_verified` must be `true`. Google can't tell students from alumni or staff, so copy says "UMD account", never "student".
- **Real names:** we store Google's name and picture, the email, and the directory ID (the email's local part). Users are keyed on the directory ID, not on `sub`: the same person has a different `sub` in the TERPmail and UMD Gmail tenants.
- **`x@terpmail.umd.edu` and `x@umd.edu` are the same user** (`users.id = 'x'`). Both addresses are recorded, one per Google identity (`user_identities.email`), whichever the person signs in with.
- **Name and picture always come from Google** and refresh at every sign-in. There's no editing in Terpsicle; `/settings` tells people to change them in their Google account.
- **The scheduler works fully signed out.** Signing in adds plan sync; Chat, writing reviews and seat alerts need it.
- **The front door** (top bar button tooltip, the Chat page signed out, the sign-in sheet): "Sign in to join your class chats. Your plans sync too." Sign-in is invited, never required, for the scheduler.
- **Session:** a cookie on terpsicle.com, set only at sign-in and removed at sign-out. Signed out, terpsicle.com sets no cookie at all.

### 4.2 The Google OIDC flow (`src/server/auth/google.ts`, pure checks in `src/core/auth`)

No OAuth library (the research found the common ones deprecated). Plain `fetch` and WebCrypto.

**`GET /api/auth/google?return=<path>`**
1. Refuse unless `SIGN_IN_ENABLED` is `"true"` (redirect to `/signin?error=unavailable`). Rate-limit per IP.
2. `return` must be a same-origin path: starts with `/`, not `//`, no backslash, at most 512 characters; otherwise `/schedule`.
3. The redirect URI is `<origin>/api/auth/google/callback`, where the origin must be one of `GOOGLE_REDIRECT_ORIGINS` (a var: `https://terpsicle.com` in production; in `.dev.vars`, the localhost origin the owner registered, which `pnpm dev` serves on port 3000). These are exactly the redirect URIs registered with Google. Any other host gets 404.
4. Make `state` (32 random bytes), `nonce` (32 random bytes) and a PKCE `code_verifier` (32 random bytes, base64url), and `code_challenge = base64url(SHA-256(verifier))`.
5. Set `__Host-oauth` = `base64url(JSON {state, nonce, verifier, return, exp: now + 10 min})` + `.` + `base64url(HMAC-SHA-256(AUTH_SECRET, payload))`, with `Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=600`. Lax is needed: the callback is a top-level GET from accounts.google.com.
6. `302` to `https://accounts.google.com/o/oauth2/v2/auth` with `client_id`, `redirect_uri`, `response_type=code`, `scope=openid email profile`, `state`, `nonce`, `code_challenge`, `code_challenge_method=S256`, `prompt=select_account` and `hd=*` (the owner's choice: the account chooser favors Workspace accounts; it's only a hint, and the server checks `hd` itself in step 5 of the callback).

**`GET /api/auth/google/callback?code&state`** (or `?error=…`)
1. Read and verify `__Host-oauth` (signature, `exp`), then clear it. Missing or bad → `/signin?error=expired`. `error=access_denied` → `/signin?error=cancelled`.
2. `state` must equal the cookie's, compared in constant time.
3. `POST https://oauth2.googleapis.com/token` (form-encoded): `code`, `client_id`, `client_secret`, `redirect_uri`, `grant_type=authorization_code`, `code_verifier`. Non-2xx → `/signin?error=google-error`.
4. Decode the `id_token` payload and validate it with `GoogleIdClaimsSchema`. No JWKS check: the token came straight from Google's token endpoint over TLS, authenticated with our client secret, which Google documents as sufficient.
5. **Claim checks**, all in `checkGoogleClaims(claims, {clientId, nonce, now})` in `src/core/auth/claims.ts`, each with a test:

   | Claim | Rule | Error code |
   |---|---|---|
   | `iss` | `https://accounts.google.com` or `accounts.google.com` | `google-error` |
   | `aud` | equals `GOOGLE_CLIENT_ID` | `google-error` |
   | `exp`, `iat` | `exp > now − 60 s`; `iat < now + 300 s` | `expired` |
   | `nonce` | equals the flow cookie's | `expired` |
   | `hd` | present and exactly `terpmail.umd.edu` or `umd.edu` | missing: `personal-account`; other: `other-domain` |
   | `email_verified` | `=== true` | `unverified-email` |
   | `email` | lowercased; its domain equals `hd` | `other-domain` |
   | local part | matches `^[a-z0-9]{2,16}$` after lowercasing; this is the directory ID | `other-domain` |
   | `name`, `picture` | optional; `name` falls back to `given_name family_name`, then to the directory ID | — |

6. Upsert the user by directory ID and the identity by `sub` (§4.4), refreshing `name`, `picture_url`, `email` (the one just used) and the identity's `email`. If the user was `deleting` (within the 7-day grace, §4.7), signing in cancels the deletion.
7. Mint a session (§4.3), set the cookie, and `303` to `return` with `?signed-in=1` (the app strips it, runs the first-sign-in merge and the `first-sign-in` install trigger).

Sign-in errors land on `/signin?error=<code>&return=…` with plain copy:
- `personal-account`: "That's a personal Google account. Choose your @terpmail.umd.edu or @umd.edu account."
- `other-domain`: "Terpsicle is for UMD accounts. Choose your @terpmail.umd.edu or @umd.edu account."
- `unverified-email`: "Google hasn't verified that email address yet. Try again once it's verified."
- `cancelled`: "You cancelled signing in. Your plans are still here."
- `expired`: "That sign-in took too long. Try again."
- `google-error` / `unavailable`: "Google didn't finish signing you in. Try again in a minute." (the second when the flag is off: "Signing in is turned off right now.")
- If UMD's Workspace settings block the app, Google shows its own error before our callback; `/privacy` and the sign-in sheet say "If Google says your organization blocked Terpsicle, UMD's Google settings stopped it."

### 4.3 Sessions (`src/server/auth/session.ts`)

- **Cookie:** `__Host-session=<token>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=2592000`. The token is 32 random bytes, base64url. Only `SHA-256(token)` (hex) is stored.
- **Sliding 30 days, with a new token:** when `POST /api/me` or a route with `auth` sees a session whose `last_seen_at` is more than 24 h old, it mints a fresh session (`expires_at = now + 30 d`) and re-sets the cookie; the old row's `expires_at` drops to a minute from now, so a tab racing this one isn't signed out. A compare-and-swap on `last_seen_at` makes one request win. At most one write a day per session.
- **A fresh token at every sign-in** (no session fixation). Sign-out deletes the row and sends the cookie with `Max-Age=0`.
- **Lookup:** `getSession(request, env, now)` → `{user, sessionId} | null`, joining `users` with `status = 'active'`. The API route table declares `auth: "none" | "user" | "admin"` per route (§12); nothing else reads the cookie.
- **Local dev:** browsers accept `Secure` cookies on `http://localhost`, so the name and attributes are the same everywhere.
- The daily job deletes expired sessions.

### 4.4 Tables (migration `0003_identity.sql`)

```sql
-- One row per person, keyed on the UMD directory ID (the email's local part).
CREATE TABLE users (
  id               TEXT PRIMARY KEY,            -- directory ID, lowercase: 'jdoe'
  email            TEXT NOT NULL,               -- lowercase, the address used at the last sign-in
  hd               TEXT NOT NULL CHECK (hd IN ('terpmail.umd.edu', 'umd.edu')),
  name             TEXT NOT NULL,               -- Google's name, refreshed at every sign-in
  picture_url      TEXT,                        -- Google's picture URL, or null
  picture_key      TEXT,                        -- USER_CONTENT key of our cached copy (§4.5), or null
  status           TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'deleting')),
  delete_after     TEXT,                        -- set while 'deleting' (§4.7)
  chat_blocked_until    TEXT,                   -- admin: no posting in Chat until then
  reviews_blocked_until TEXT,                   -- admin: no writing reviews until then
  created_at       TEXT NOT NULL,
  last_sign_in_at  TEXT NOT NULL
);

-- Google subjects seen for a user. Two per person is normal (TERPmail and UMD Gmail).
CREATE TABLE user_identities (
  provider    TEXT NOT NULL CHECK (provider = 'google'),
  sub         TEXT NOT NULL,
  hd          TEXT NOT NULL,                  -- terpmail.umd.edu or umd.edu
  email       TEXT NOT NULL,                  -- that tenant's address: both of a person's emails are kept
  user_id     TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  created_at  TEXT NOT NULL,
  PRIMARY KEY (provider, sub)
);
CREATE INDEX user_identities_by_user ON user_identities (user_id);

CREATE TABLE sessions (
  id_hash       TEXT PRIMARY KEY,               -- hex SHA-256 of the cookie token
  user_id       TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  created_at    TEXT NOT NULL,
  last_seen_at  TEXT NOT NULL,
  expires_at    TEXT NOT NULL
);
CREATE INDEX sessions_by_user ON sessions (user_id);
CREATE INDEX sessions_expiry ON sessions (expires_at);
```

- If a `sub` already maps to a different `user_id` (it shouldn't: a directory ID doesn't change), the callback refuses with `google-error` and logs a count-only server event.
- Rows are validated on read with `UserRowSchema` and `SessionRowSchema` (`src/server/auth/store.ts`), like `alerts/store.ts`.

### 4.5 Profile pictures

Stored as a cached copy, not hot-linked:
- at sign-in, when `picture` changed, the Worker fetches it at 96 px (`=s96-c`), checks it's `image/jpeg|png|webp` under 200 KB, and puts it in R2 `USER_CONTENT` at `avatars/<userId>/<hash16>.<ext>` (hash = first 16 hex of SHA-256 of the bytes); `users.picture_key` points at it, and the old object is deleted. A failure leaves the old copy, or none (initials are shown). (Landed with `v2/identity`.)
- served at `/avatars/<userId>/<hash16>.<ext>` only with a valid session (`private, max-age=86400, immutable`), so profile pictures aren't public and the CSP stays `img-src 'self'`;
- viewers' IPs never reach Google, and the picture keeps working if Google's URL changes;
- account deletion removes the objects.

### 4.6 How PR previews sign in: a fixed test mode

Google forbids wildcard redirect URIs, and previews live at `pr-<n>-terpsicle.zsrobinson.workers.dev`. **Previews use a fixed test mode, not the real Google flow.**

- `AUTH_TEST_MODE: "true"` is set in `wrangler.jsonc`'s `previews.vars`, and by `vite.config.ts` for `pnpm dev:mock` (and so e2e). It's never set in production vars.
- Test mode is on only when `AUTH_TEST_MODE === "true"` **and** the host is a PR preview (`pr-<n>-terpsicle.zsrobinson.workers.dev`) or localhost, so never `terpsicle.com` or `www.terpsicle.com`, whatever the vars say. A worker test asserts that the top-level `vars` in `wrangler.jsonc` don't set it.
- `/auth/test` lists the fixture identities from `src/fixtures/users.ts` (`TEST_USERS`: `tstudent` "Test Student", `tclassmate` "Test Classmate", `tadmin` "Test Admin"), each with "Sign in as …". The button `POST`s `/api/auth/test-sign-in {userId, return}`, which upserts that user and mints a normal session. Everything after sign-in (sessions, sync, chat, reviews) runs the real code.
- In test mode, and only there, the fixture user `tadmin` is an admin (`TEST_USERS` marks it). The Google button shows "Sign in (test mode)" and goes to `/auth/test`.

**Why not a broker on terpsicle.com** (the callback lands on terpsicle.com and hands a one-time code back to the preview):
1. **Previews run unreviewed code.** A broker would give real Google identities (names, emails, pictures) to any PR's code, and would add a production endpoint that trusts `*.workers.dev` origins.
2. **Previews have their own D1** (`terpsicle-preview`), so a code minted in production D1 would need a server-to-server redemption API with a shared secret on both sides: more production surface for a test convenience.
3. **CI and e2e need a deterministic sign-in anyway.** Google can't be driven headlessly in CI, so test mode would exist regardless; a broker would be a second mechanism.
4. **What test mode doesn't cover is small and tested elsewhere:** claim checks are pure and unit-tested with real-shaped claims; the redirect is exercised on localhost (the owner registered a localhost callback) and in production. The deploy smoke check asserts `GET /api/auth/google` answers `302` to `accounts.google.com` with the right `client_id`, `redirect_uri`, `scope` and `code_challenge_method`.

### 4.7 Sign-out and account deletion

- **Sign out** (`POST /api/auth/sign-out {removeLocal, pushEndpoint}`): deletes the session and this device's push subscription, clears the cookie. Plans stay on the device and stop syncing. The menu offers two items: "Sign out" (tooltip "Your plans stay on this device") and "Sign out and remove plans from this device" (for a shared computer), which also clears Dexie's plans, blocks, colors, sync state and the `terpsicle:returning` flag.
- **The next sign-in on a device** merges whatever is local into that account, the same as a first sign-in (§5.4). That's why shared computers get the "remove plans" option.
- **Delete the account** (`POST /api/account/delete`): no dialog. It sets `status = 'deleting'` and `delete_after = now + 7 d`, deletes every session and push subscription, and signs out. The page says "Your account will be deleted on Oct 3. Sign in before then to keep it." Undo in the toast signs you back in through Google. The daily job purges accounts past `delete_after`:
  - `users` row (cascades: identities, sessions, sync rows, watches, settings, notifications, chat membership tables);
  - reviews stay published with `author_id` set to null ("Your published reviews stay up, with no name on them. Delete them first if you want them gone.");

## 5. Plan sync

### 5.1 Model

- **Plain server-side storage**, encrypted at rest by D1/Cloudflare, **not end-to-end encrypted.** This is the orchestrator's decision, flagged for the owner (§14): with Earshot shelved, it lets Chat derive your rooms from your plan and keeps recovery simple. There are no sync keys, passkeys or recovery codes.
- **Deliberately not a sync engine.** The unit of sync is a **document**, saved whole with the server `rev` it was based on (compare-and-swap). Plans are never merged field by field. One person usually uses one device at a time, so conflicts are rare, and when one happens the person sees both versions.
- **Dexie stays the source of truth on each device.** The scheduler works offline and signed out exactly as today; sync copies docs up and down.
- **Docs** (`src/core/schema/sync.ts`; mapping to and from the Dexie tables in `src/core/sync/docs.ts`):
  - a **plan doc** per plan: the `Plan` row itself (term, name, tab order, courses with their sections, snapshots and saved-for-later entries);
  - one **settings doc** per user for what no single plan owns: blocks (per term, shared by the term's plans, DATA.md §5), course colors (global), travel settings, and `chatPlans` (§8.2).
- **Not synced:** UI prefs (tab, sidebar, theme, open drill-in), `activePlanByTerm`, generate drafts, the data cache. Seat watches are server-side already (§6.5).
- **Signing in turns sync on.** There's no separate toggle.

### 5.2 D1 (migration `0005_sync.sql`)

```sql
CREATE TABLE sync_docs (
  user_id     TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  kind        TEXT NOT NULL CHECK (kind IN ('plan', 'settings')),
  doc_id      TEXT NOT NULL,     -- plan: its LocalId; settings: 'settings'
  term_id     TEXT,              -- plans; null for settings
  rev         INTEGER NOT NULL,  -- from sync_heads.head at the save
  body        TEXT,              -- JSON (PlanDocSchema / SettingsDocSchema); null = tombstone
  updated_at  TEXT NOT NULL,     -- server time of the save
  PRIMARY KEY (user_id, kind, doc_id)
);
CREATE INDEX sync_docs_since ON sync_docs (user_id, rev);

CREATE TABLE sync_heads (
  user_id         TEXT PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
  head            INTEGER NOT NULL,           -- the latest rev handed out
  pruned_through  INTEGER NOT NULL DEFAULT 0  -- tombstones with rev <= this are gone
);
```

One JSON row per doc. Revs come from the user's counter, so "every doc with `rev` > n" is a pull cursor. Bodies are validated with `SyncDocSchema`'s body schemas, and a plan body's `id` must be its `doc_id`. Limits: a body ≤ 64 KB, ≤ 200 live plan docs per user, ≤ 50 docs per push. Tombstones are pruned **30 days** after `updated_at` by the daily job, which raises `pruned_through`.

### 5.3 The API (`src/server/sync/`, `auth: "user"`)

- **`POST /api/sync/push`** `{docs: [{kind, id, baseRev, body | null}]}` (null = delete) → `{results: [{kind, id, status: "ok", rev} | {kind, id, status: "conflict", doc: SyncDoc}]}`. Each doc is saved only if its stored `rev` equals `baseRev` (0 = "new"): one conditional upsert per doc that takes the next `head`. Docs are independent; a conflict on one doesn't stop the others. A conflict returns the server's current doc for §5.4.
- **`POST /api/sync/pull`** `{since}` → `{status: "ok", cursor, docs: SyncDoc[], more}` (rev > `since`, ascending, ≤ 200 per page) or `{status: "reset"}` when `since < pruned_through`: the device pulls everything and treats it like a first sign-in (§5.4).
- **Chat membership is derived server-side from the stored docs:** a push that saves a plan doc or the settings doc rewrites that user's `chat_members` for the affected terms (§8.2), in the same batch.

**The device** (`src/features/sync/engine.ts`; flags from `planSyncReducer` in `src/core/sync/state.ts`):
- **No op log.** Each doc has a `rev` (0 = never saved) and a `dirty` flag, plus `inFlight` while a push is out. An edit marks the docs it changed dirty (`changedDocKeys`); applying a server doc never does.
- push: the latest state of every dirty doc, 1 s after a change and when back online;
- pull: on load, on `visibilitychange` to visible, and every 60 s while visible. A pulled doc replaces the device's version only when that doc isn't dirty or in flight; a dirty one is left for its push, whose compare-and-swap reports the conflict.
- **Dexie v2** (`LOCAL_DB_VERSION` 1 → 2, with an `upgrade()`): a `syncDocs` table keyed by doc key (`plan:<id>` or `settings`): `{key, rev, dirty, inFlight}` (in-flight docs are made dirty again on load); the settings doc's `base` (its body as last saved or pulled, for §5.4); a `sync` settings row `{userId, cursor}`; `seatAlerts` is dropped (§6.5).

### 5.4 Conflicts, undo and the first sign-in (`src/core/sync/`, pure, property-tested)

- **A plan doc conflict** (the server's rev moved): nothing is merged. The server's version stays as the plan, and this device's becomes a **new plan** named "<name> (copy)" ("(copy 2)", … on repeats; a copy of a copy counts on from the original name) at the end of the term's tabs. If both hold the same work (term, name and courses; tab order and timestamps don't count), the server's is simply taken. **An edit beats a delete** either way: a plan deleted elsewhere but edited here is saved again; one deleted here but edited elsewhere comes back.
- **A settings doc conflict:** it can't be kept twice, so it's settled per key (a block, a course's color, the travel settings, a term's chat plan). Keys this device changed since its `base` keep its value; every other key takes the server's; a key deleted on one side and edited on the other keeps the edit.
- **Undo stays local.** A server doc that replaces a plan becomes the new state, and that plan's undo history is cleared.
- **First sign-in on a device** (`firstSignInUnion`): pull everything, then upload every local plan the server doesn't have, after the account's tabs in its term. A local plan with the same term and name as a synced one gets "(copy)". A plan the account already has but that differs here (signed in before, edited while signed out) is kept both ways, as in a conflict. **Nothing is dropped**, with one exception: an untouched auto-created plan (a default "Plan X" name and no courses) isn't uploaded into a term where the account already has plans, or every new device would add an empty tab. The settings doc keeps the account's values for keys both sides have and adds what only this device has. A toast says "Your 3 plans are on your account now. Nothing was dropped."
- **Sign-out** keeps local plans unless the person picks "Sign out and remove plans from this device" (§4.7).

### 6.4 Web push with VAPID from Workers (`src/server/push/`)

No Node library; WebCrypto only, so it runs in the Worker and the Durable Object.
- **Keys:** a P-256 key pair. `VAPID_PUBLIC_KEY` (var, base64url uncompressed point, handed to the client in `/api/me`), `VAPID_PRIVATE_KEY` (secret, the JWK's `d`), `VAPID_SUBJECT` (var, `mailto:alerts@terpsicle.com`). `scripts/vapid-keys.ts` generates them.
- **VAPID (RFC 8292):** an ES256 JWT `{aud: <endpoint origin>, exp: now + 12 h, sub: VAPID_SUBJECT}`, signed with `crypto.subtle.sign({name: "ECDSA", hash: "SHA-256"})` (raw r‖s is what ES256 wants), sent as `Authorization: vapid t=<jwt>, k=<public key>`. JWTs are cached per push-service origin for an hour.
- **Payload encryption (RFC 8291, `Content-Encoding: aes128gcm`):** ephemeral ECDH P-256, HKDF-SHA-256, AES-128-GCM, one record. The unit test uses RFC 8291 Appendix A's example (fixed keys and salt) and must reproduce its ciphertext byte for byte.
- **Headers:** `TTL` (seat-open 3600; chat 86400), `Urgency` (seat-open `high`; chat `normal`), `Topic` for collapsing (a base64url hash ≤ 32 chars: per section for seat-open, per room for chat).
- **Payload** (`PushPayloadSchema`, ≤ 3 KB): `{v: 1, type, title, body, url, tag}`, e.g. `{type: "chat-reply", title: "Hannah Lee replied in CMSC131 · 0303", body: "check that you compare the names with .equals", url: "/chat/202701/CMSC131/section-0303?m=01J…", tag: "chat:202701:CMSC131:section-0303"}`.
- **Results:** 201 → `last_success_at`; 404/410 → delete the subscription; 429/5xx → `failure_count += 1`, delete after 10 consecutive failures; each send logs a `notification_deliveries` row.
- **Caps:** at most 30 chat pushes per user per hour (tags collapse the rest on the device anyway); seat-open keeps its alert caps (§6.5).
- `PUSH_ENABLED` (var) off → every push is `skipped`; previews have it off.

## 7. Reviews (Terpsicle Reviews)

### 7.1 Rules
- **Anyone can read**, with no sign-in.
- **Writing and reporting require sign-in**, which proves a UMD account.
- **Anonymous to readers.** The backend stores the author (`reviews.author_id`), so people can edit and delete their reviews and limits work. **Nothing shown to readers, to the admin, or to moderation carries the author's identity** (§7.5).
- **Model-first moderation** (§9): clean reviews publish on their own; only uncertain or flagged ones reach the owner in `/admin`.
- **The scheduler** keeps, in course details: the numbers (rating, count, average GPA, grade bars), the AI summary with its sparkles, and a link, "Read reviews" → `/reviews/instructors/<id>?course=<code>`. Full reviews and writing live at `/reviews` only.
- **PlanetTerp ingestion stays** (hardened in #39). **Stored PlanetTerp review text stays off** (`PLANETTERP_KEEP_REVIEW_TEXT` unset) until PlanetTerp agrees; until then PlanetTerp reviews appear as counts, in summaries (fetched live, as today) and as a credited link ("48 more on PlanetTerp"), never as text on our pages.
- **Never edit a review's words.** We publish, hold or remove whole reviews.

### 7.2 Instructor ids

A review needs an instructor id that doesn't depend on PlanetTerp. The id is the PlanetTerp slug when the name join knows the instructor (so `summaries/<slug>.json` and links keep working), else a minted `t~` + 10 base32 characters. `InstructorSlugSchema` must accept both (widen its pattern in the reviews PR).

### 7.5 Anonymity rules
1. `PublicReviewSchema` is `{id, course, termId, rating, grade, body, createdMonth: "YYYY-MM", edited: boolean}`: no author field, no user-derived id, and the date rounded to the month to blunt timing guesses.
2. `author_id` never leaves `src/server/reviews/store.ts` except as a boolean ("is this yours") and for limits. Admin and moderation payloads (`AdminReviewItemSchema`) have no author field; a worker test asserts every admin and public payload is free of `author`, `userId`, directory IDs and emails.
3. Admin actions against an author go through the review id: "Stop this author writing reviews for 30 days" sets `reviews_blocked_until` without showing who.
4. No review id, instructor id or course code in analytics events about writing; no author id in logs.
5. `/reviews/policy` says it honestly: "We store which account wrote a review so you can edit or delete it and so limits work. We never show it to readers or moderators."

### 7.6 Merging with PlanetTerp data
- **R2 family `reviews/`** (served, written by the hourly `reviews-publish` job):
  - `reviews/manifest.json` (`ReviewsManifestSchema`: `{schemaVersion, generatedAt, departments: [{code, hash}]}`), `no-cache`, edge 1 h;
  - `reviews/dept/<DEPT>.<hash>.json` (`ReviewsDeptSchema`: per instructor id `{rating, reviewCount, latestReviewAt}` from published Terpsicle reviews, plus `names` for minted instructors), hashed and immutable.
  - A new `SCHEMA_VERSIONS.reviews` family. Review **text** is never in R2 (hashed files are immutable for a year, and a removal must be instant); it comes only from `reviews/list`.
- **Combined numbers** (`combineRatings` in `src/core/reviews/combine.ts`): `rating = Σ(rating_s × count_s) / Σ count_s` over PlanetTerp and Terpsicle; `reviewCount = Σ count_s`; the tooltip gives the parts ("4.2 from 61 reviews: 4.1 from 48 on PlanetTerp, 4.6 from 13 on Terpsicle"). Grade distributions stay PlanetTerp's; self-reported grades never mix in.
- **Summaries:** `review-summary` reads our published reviews from D1 plus PlanetTerp's live, newest 40 overall within the existing 18k-character budget. Freshness compares against the combined count. `ReviewSummarySchema` gains optional `sources: {planetterp, terpsicle}` (additive). Summaries also go through Llama Guard's S5 (defamation) check before they're stored; unsafe → not shown.
- **Copies:** stage 0 rejects text matching a published Terpsicle review of the same instructor ("This review is already posted."). Cross-posts from PlanetTerp can't be detected without its text; that's accepted.

## 8. Chat (Terpsicle Chat)

### 8.1 Rooms, derived (`src/core/chat/rooms.ts`)

Rooms come from the catalog with the grouping course details already uses (`src/core/catalog/section-groups.ts`). Nobody creates a room.

As built (#49, then the owner's one-level grouping, 2026-09-26): ids are `RoomId`s in `src/core/schema/chat.ts` (DATA.md §1).

```ts
// "202701:CMSC131", "202701:CMSC131:P:pedram-sadeghian", "202701:CMSC131:0303"
export function roomsForCourse(termId: TermId, course: Course): RoomTree;   // pure, cached per course
export function roomsForSection(tree: RoomTree, sectionCode: SectionCode): Room[];
export function myRooms(plan: Plan, index: CatalogIndex): Room[];
```

Rules (the owner, 2026-09-26: one level of grouping, like course details):
1. Every course has a course room ("CMSC131 · everyone"). With one section, that's the only room.
2. With two or more sections, every section gets a room.
3. With more than one professor, each named professor gets a room between the course and their sections ("Sadeghian's sections"). One professor: the course room is theirs. TBA sections sit right under the course room. **No lecture rooms:** section codes already say which sections share a lecture.
4. The room list groups like course details (`groupSectionsByInstructor`): by professor, sections sorted by code, with no heading when there's one professor; past `MANY_SECTIONS` (20), groups start collapsed and yours are pinned on top.
5. Section rooms are named by all their meetings ("0303 · MWF 11am and TuTh 11am discussion", "IRB 0324, CSI 1121").

Edge cases: labs name like discussions; a section with no set time still gets its room ("0101 · online, no set time"); a time or room change renames in place (history stays); a cancelled section's room turns read-only with one quiet line pointing to the course room; cross-listed codes get separate rooms.

### 8.2 Your rooms and who can read them

- **Your rooms come from your synced plan's sections.** Per term, one synced plan is your chat plan: the settings doc's `chatPlans` (`{[termId]: planId}`, §5.1), defaulting to the plan with the lowest `order` in the term. The chat list shows "Rooms from Plan A ▾" to change it. Your rooms: for each course in that plan, its course room, plus the professor and section rooms of the placed section; for bookmarked courses, the course room only.
- **Course rooms are open** to any signed-in user, including people still deciding: course details has "Open CMSC351 chat", which adds a `chat_follows` row so it stays in your list.
- **Professor and section rooms** need one of their sections in **any** of your synced plans for that term. It's on trust, and room info says so: "14 people have 0303 in a plan. Terpsicle can't see registrations."
- **Mute** per room (`chat_room_prefs`); leaving a course room you follow deletes the follow. Undo, never a dialog.

`chat_members` is a per-user index of chat-plan sections, derived on the server from the stored docs and rewritten in the sync push batch whenever that user's chat plan (or its choice) changes. It powers member counts, @-mention autocomplete and "people in this room". It describes people, not rooms, so it doesn't break §8.3's rule.

### 8.3 Nothing is stored for a room until its first message

- Rooms are computed in the browser (catalog + synced plan) and in the object (catalog), never listed from storage.
- The `CourseChat` object for a course is only addressed when someone opens that course's chat; a Durable Object that never writes has no storage.
- The first message in a room creates its `rooms` row in the object and its `chat_rooms` row in D1. Before that, the room shows "No messages yet. Say hi to your classmates."
- Unread counts for the chat list come from one D1 query over `chat_rooms` and `chat_read_markers`, so opening `/chat` wakes no objects.

### 8.4 The `CourseChat` Durable Object

- **One object per course per term:** `env.COURSE_CHAT.idFromName("<termId>:<courseCode>")`, class `CourseChat` in `src/server/chat/course-chat.ts`, exported from `src/server.ts`. SQLite storage and the WebSocket Hibernation API (`ctx.acceptWebSocket`, `serializeAttachment`, `setWebSocketAutoResponse` for ping/pong). Why this size (the Chat canvas's architecture board): a course's rooms move together, one socket covers every room of a course, and even ENGL101 (93 rooms) or CMSC131 (~600 people) is far below one object's limits. One object per room would mean 93 objects and a reconnect per room switch; one per campus would put every message at UMD through one thread.
- **It reads the catalog** from R2 `DATA` (`catalog/<term>/manifest.json` → the course's department chunk) to build its `RoomTree` with `chatRooms`, cached in memory and refreshed when older than an hour.
- **It reads D1** (`DB`) for profiles, plan-based authorization, settings and push subscriptions, and writes `chat_rooms`, `chat_read_markers`, `chat_author_courses` and `notifications`.

**Object storage (SQLite inside the object):**

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);   -- term_id, course_code, read_only_at, delete_at
CREATE TABLE rooms (                                          -- a row only after the first message
  room_id      TEXT PRIMARY KEY,
  last_seq     INTEGER NOT NULL,
  created_at   TEXT NOT NULL
);
CREATE TABLE messages (
  id          TEXT PRIMARY KEY,         -- time-sortable, 26 chars (ULID), minted by the object
  room_id     TEXT NOT NULL,
  seq         INTEGER NOT NULL,         -- per room, from 1; clients resume from it
  author_id   TEXT NOT NULL,            -- users.id
  body        TEXT NOT NULL,            -- plain text, 1–2,000 characters
  reply_to    TEXT,                     -- a message id in the same room
  mentions    TEXT NOT NULL DEFAULT '[]', -- JSON array of user ids, ≤ 5
  status      TEXT NOT NULL CHECK (status IN ('pending', 'visible', 'held', 'removed')),
  labels      TEXT NOT NULL DEFAULT '[]', -- moderation labels
  client_id   TEXT NOT NULL,            -- sender's idempotency key
  created_at  TEXT NOT NULL,
  edited_at   TEXT,
  UNIQUE (author_id, client_id),
  UNIQUE (room_id, seq)
);
```

A message deleted by its author is deleted at once (row gone, a `deleted` event broadcast).

**`GET /api/chat/socket?term=<termId>&course=<code>`** (`Upgrade: websocket`). The Worker checks `CHAT_ENABLED` (not `off`), the session, `Origin` (§12), the rate limit, and that the term is known; then forwards to the object with `X-Terpsicle-User: <userId>` (the object is reachable only through the Worker, so it trusts that header). The socket's attachment holds `{userId, readableRooms, connectedAt}`.

**Protocol** (`src/core/schema/chat.ts`, JSON text frames, validated both ways):

```ts
// client → server
{ t: "hello", v: 1, since: Record<RoomId, number> }   // last seq seen per room; server replays after it (≤ 200 per room, else "gap")
{ t: "history", room: RoomId, before: number, limit: number }   // ≤ 50
{ t: "send", room: RoomId, clientId: string, body: string, replyTo: string | null, mentions: string[] }
{ t: "edit", id: string, body: string }
{ t: "delete", id: string }
{ t: "read", room: RoomId, seq: number }
{ t: "refresh" }                                     // after a sync: recheck which rooms you can read

// server → client
{ t: "ready", me: UserId, rooms: RoomState[], readOnly: boolean }        // RoomState: {room, lastSeq, unread, canPost, members}
{ t: "messages", room: RoomId, messages: ChatMessage[], gap: boolean }   // replay and history
{ t: "message", message: ChatMessage }                                   // new, edited, held (author only), removed
{ t: "deleted", room: RoomId, id: string }
{ t: "ack", clientId: string, id: string, status: "pending" | "visible" | "held" }
{ t: "profiles", users: { id: UserId, name: string, avatarUrl: string | null }[] }
{ t: "error", code: "rate-limited" | "not-allowed" | "read-only" | "invalid" | "unavailable" | "blocked", clientId?: string, retryAfter?: number }
```

`ChatMessage` = `{id, room, seq, authorId, body, replyTo, mentions, status, createdAt, editedAt}`. Names and pictures travel separately in `profiles` (sent for authors the client hasn't seen), from D1 `users`.

**Sending:**
1. Validate (length, room readable, not read-only, not `chat_blocked_until`, limits: 10 messages per 30 s per user per course, 500 per day).
2. Store as `pending`; ack `pending` to the sender, who sees it at once in muted style.
3. Screen with the moderation service (§9), surface `chat`. Allowed → `visible`, broadcast to sockets that can read the room; held → `held`, sent to the author only with the note (§9.2). A model error is retried by an alarm within 5 minutes before the message goes to the human queue.
4. Once visible: update `chat_rooms` in D1, record `chat_author_courses` on the author's first message in the course, and for each mention (a member of the course, not the author) and the replied-to author, insert a `notifications` row and, per their settings and if not connected here, send a push (`ctx.waitUntil`).

`CHAT_ENABLED: "read"` answers `send` with `unavailable` (reading works); `off` refuses sockets.

**Retention (DO alarms):**
- **Read-only** at the term's `classesEnd` + 10 days (from `calendar/<term>.json`), or when `terms.json` marks the term archived if the calendar isn't published. Rooms then show "This term's over. The rooms stay readable until Feb 19."
- **Deleted** 60 days after read-only: `ctx.storage.deleteAll()`, plus the D1 rows for that course and term (`chat_rooms`, `chat_read_markers`, `notifications`, `chat_author_courses`).
- The alarm is first set with the first message. Moderation snapshots of chat items are blanked 30 days after a decision (§9.4). There's no export at launch.

**Not in the first release:** reactions, pins, threads beyond one-level replies, search, images and files, typing indicators, per-course display names (Chat uses real Google names and pictures; no pseudonyms).

## 9. The shared moderation service

One service for reviews and chat: `src/server/moderation/` (Worker side), with the pure rules and policy in `src/core/moderation/`.

```ts
export type Surface = "review" | "chat";
export type Verdict = "allow" | "hold" | "reject";
export async function screen(
  env: ModerationEnv,
  item: { surface: Surface; ref: string; text: string; context: ScreenContext },
  opts: { now: Date },
): Promise<ScreenResult>;
// ScreenResult: {verdict, labels: ModerationLabel[], urgent: boolean, stage: "rules" | "model",
//                guard: GuardResult | null, policy: PolicyResult | null, error: string | null}
```

It always writes a `moderation_decisions` row and, for `hold`, a `moderation_queue` item. Tests use a `rulesOnlyScreen` adapter and a mocked `AI` binding; `pnpm dev:mock` uses the rules-only adapter.

### 9.1 Stage 0: rules (`src/core/moderation/rules.ts`, instant, pure)

| Rule | Review | Chat |
|---|---|---|
| Length | 40–2,000, else inline error | 1–2,000, else `invalid` |
| URL | inline error, nothing stored | allowed; answer-site domains (`ANSWER_SITE_DOMAINS`: chegg.com, coursehero.com, quizlet.com, …) → hold `graded-work` |
| Email address, phone number, 9-digit UID | inline error | hold `personal-info` |
| Copy of a published review (same `text_hash`) | inline error | — |
| 15+ lines that look like code, or a numbered list of 5+ short answers | — | hold `graded-work` |

### 9.2 Stage 1: Workers AI with Meta models

Both calls run in parallel through the `AI` binding, with the text fenced as untrusted data (the pattern in `src/server/summaries/prompt.ts`).

- **Llama Guard 3** (`@cf/meta/llama-guard-3-8b`): `safe`, or `unsafe` with hazard categories S1–S14.
- **A Llama instruct model** for policy and quality, in JSON mode, validated with `PolicyResultSchema`:
  ```ts
  { verdict: "ok" | "check" | "not-allowed", confidence: number /* 0–1 */,
    labels: Array<"personal-info" | "names-a-student" | "slur-or-hate" | "threat" | "sexual" | "self-harm"
                | "misconduct-claim" | "appearance" | "off-topic" | "heavy-profanity" | "graded-work"
                | "not-a-review" | "spam"> }
  ```
  Reviews use `@cf/meta/llama-3.3-70b-instruct-fp8-fast` (already vetted, DATA.md §7.2). Chat needs a faster answer: the moderation PR measures that model against a smaller current Llama instruct model on a labeled set and picks the one with p95 under 2 s and no missed `graded-work` cases, recording the result in STATUS.md. Model ids are constants in `src/server/moderation/models.ts`.

**Thresholds** (`src/core/moderation/policy.ts`, constants with tests):

| Signals | Review | Chat |
|---|---|---|
| Guard `safe`, policy `ok` with confidence ≥ `ALLOW_CONFIDENCE`, no labels | **allow** (0.8) | **allow** (0.6) |
| Policy `ok` below that confidence | hold | hold |
| Any label, or guard `unsafe` | hold | hold |
| `threat` label, or guard S1 (violent crimes) | hold, **urgent** | hold, **urgent** |
| `self-harm` label, or guard S11 | hold; the author sees a care line with 988 and the UMD Counseling Center | same |
| Policy `not-allowed` with `not-a-review` or `spam`, confidence ≥ 0.9, and guard `safe` | **reject** ("This doesn't read like a review of the teaching.") | hold |
| Model error, invalid output, or over `MODERATION_DAILY_CAP` | hold (fails closed) | retried by alarm within 5 min, then hold |

Nothing publishes because it waited. What a held author sees, in plain words and never in red: reviews, "A person will look at this first. That usually takes a few days. You can edit it while it waits."; chat, "Only you can see this. It looks like it could be graded work, so a person will check it first. Edit or delete it any time." (the label picks the sentence).

**Keep the human queue small.** The admin stats page shows the share of items held per surface per week. The target is under 5%; above 10% for a week, tune the thresholds or the prompt (a STATUS.md decision each time).

### 9.3 Reports

`reports/create {surface, ref, reason, note | null}` (`auth: "user"`), one per user per item. Reasons: `personal-info`, `names-a-student`, `hate`, `threat`, `sexual`, `misconduct-claim`, `graded-work`, `off-topic`, `other`. An item is **hidden** until a person decides when 3 different people report it, or 1 reports `threat`, `personal-info` or `names-a-student`. Every report puts the item in the queue. All reporters weigh 1; there are no trust tiers.

### 9.4 D1 (migration `0004_moderation.sql`)

User ids here are plain `TEXT` without foreign keys, so this migration and `0003_identity.sql` can merge in either order.


## 12. Security

**CSRF**
- Every `/api/*` call stays `POST` with `Content-Type: application/json` (a cross-site form can't send that without a preflight, which is never granted), `z.strictObject` inputs, no CORS headers.
- **Plus an origin check** (`src/server/security/origin.ts`) on every route with `auth: "user" | "admin"` and on the WebSocket upgrade: `Origin` must equal the request's own origin, and `Sec-Fetch-Site`, when present, must be `same-origin`. Otherwise `403`.
- The session cookie is `SameSite=Lax`, so cross-site subresource requests never carry it.
- The OIDC flow is bound to the browser by `state` in the signed `__Host-oauth` cookie (which also stops login CSRF), plus PKCE and `nonce`.
- Sign-out and every change are `POST`; no GET changes state (email one-click links are `POST` per RFC 8058; a GET to them shows a button).

**Rate limits.** The route table in `src/server/api/router.ts` gains `auth` and `perUserPerHour` next to `perIpPerHour`. Per-IP keys stay `HMAC(CF-Connecting-IP)`; per-user keys are `user:<id>:<route>`; both use `counters`.

**CSP** (set by the Worker on HTML responses, `src/server/security/headers.ts`):

```
default-src 'self';
script-src 'self' <sha256 hashes of the known inline head scripts>;
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
font-src 'self';
connect-src 'self' wss://terpsicle.com;
worker-src 'self' blob:;
manifest-src 'self';
object-src 'none';
base-uri 'none';
form-action 'self';
frame-ancestors 'none';
upgrade-insecure-requests
```

- `wss://` is listed for Safari versions that don't match it with `'self'`; previews and localhost use their own origin.
- `blob:` workers are for MapLibre; `'unsafe-inline'` styles are for Radix and Tailwind's runtime style attributes.
- The inline head scripts (load recovery, the `/` returning check) get hashes computed at build time. The CSP ships first as `Content-Security-Policy-Report-Only` for a week, then enforced.
- Also: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`, and HSTS on the zone.

**Rendering user content.** Review and message text is rendered as text, never `dangerouslySetInnerHTML`. Links in chat are detected client-side and rendered with `rel="noopener noreferrer ugc" target="_blank"`.

**Secrets and logs.** Session tokens, flow cookies, VAPID keys and emails never go into logs or analytics. Admin checks read only the bundled `config/admins.txt` (plus `tadmin` in test mode).
