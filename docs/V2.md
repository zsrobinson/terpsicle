# Terpsicle v2: technical plan

The plan every v2 agent builds from. It turns the owner's decisions of 2026-09-26 into names, tables, routes and an order of work, so agents working in parallel converge on the same contracts.

**Precedence.** The owner's decisions win, then this document, then the older docs. Where `SPEC.md`, `DESIGN.md`, `BUILD.md`, `DATA.md` or `ANALYTICS.md` still say otherwise, this document wins and the implementing PR fixes the older doc. Once a table or schema lands in code, the code wins (`DATA.md`'s rule) and the PR updates this document too. Anything not decided here: pick the simplest option consistent with this file, `DESIGN.md` §5 and `SPEC.md` §3.13, and state the interpretation in the PR.

**v3.** Terpsicle Plan (`/plan`) and Terpsicle Todo (`/todo`) join the suite; their plan is `docs/V3.md`, built on this one. The product order is by color everywhere products are listed: Schedule, Reviews, Chat, Plan, Todo.

**Out of scope.** Earshot and Orgs are on the back burner. Don't build them, and don't add their code paths, tables, routes, bindings or flags. The research drafts' Earshot parts (anonymous credentials, pseudonyms, the `earshot` Worker, the `Campus` object) are shelved with them.

## 2. Routing rules for `/`

1. **The installed PWA** starts at `start_url: "/home"` (Home, `docs/V3.md` §1.5; `/schedule` before it), so it never sees `/`.
2. **A session goes straight to `/schedule`.** The Worker handles `GET /` before the app: if the request has a `__Host-session` cookie (presence only, no D1 lookup), it answers `302 Location: /schedule`. An expired cookie costs one extra hop, nothing worse.
3. **Saved local data goes straight to `/schedule`.** Local data lives in IndexedDB, which only the browser can read:
   - the scheduler sets `localStorage["terpsicle:returning"] = "1"` whenever the plans store holds at least one plan (and clears it after "Sign out and remove plans from this device");
   - a tiny inline head script on `/` checks that key synchronously, before first paint, and calls `location.replace("/schedule" + location.search)`;
   - if the key is missing (storage cleared, or data from before this change), the same head script counts plans in IndexedDB directly (`plans.count() > 0`; no Dexie on `/`), sets the flag again and replaces then. The marketing content renders hidden until that check finishes, at most 150 ms, so returning visitors don't see a flash. When the router navigates to `/` from another page, the route's `beforeLoad` applies the same check.
4. **Everyone else sees the marketing page.**
5. **`/?stay`** always shows the marketing page, so "About Terpsicle" in the product menu can link to it without bouncing.

The rule lives in `src/features/marketing/returning.ts` (a pure `shouldSkipMarketing({hasSessionCookie, returningFlag, planCount})` in `src/core/routing` so it's testable; the head script inlines it) and `src/server/routing.ts` for the cookie hop. Both redirects keep the query string. The page itself is the owner's pick from the round-4 prototypes (`v3/marketing-live`; docs/DESIGN.md §8, docs/V3.md §1.4): the hero over the plain week, then one step per product beside a sticky sample of the scheduler that each step adds to. Its one primary button is "View schedule"; sign-in is a plain link to `/signin`, and a signed-in visitor never sees it. The Worker serves `/robots.txt` and `/sitemap.xml` (`src/server/seo/`, entries in `src/core/seo/sitemap.ts`, where Reviews adds its public pages), and `public/og.png` is drawn from the hero by `scripts/build-og-image.ts`.

### 3.2 Service worker (`/sw.js`, `src/server/service-worker.ts`)

One service worker at scope `/`. It keeps today's rules (STATUS.md, "Service worker") and adds push. Bump `SERVICE_WORKER_VERSION` to 2.

| Requests | Strategy |
|---|---|
| Navigations under `/schedule`, `/reviews`, `/chat`, `/settings`, `/admin`, `/signin`, `/privacy`, `/` | Network-first. On network failure, the cached copy of that path, else the most recently cached page (every path serves the same SPA shell). |
| Navigations to `/api/*` (sign-in) and `/auth/*` (test mode) | Network only, never cached, never a fallback. |
| `/assets/*` | The app shell's files (the entry, each route's chunk, their static imports and CSS, listed by the client build) are precached at install; the rest are cache-first as fetched, capped at 400 files. |
| Other requests to `/api/*` (including the WebSocket), `/data/*`, `/ingest/*`, `/avatars/*`, `/auth/*` | Pass through. `/api` answers are per person and must never be cached. |

Push handlers, in the same file:
- `push`: parse `PushPayloadSchema` (`{v: 1, type, title, body, url, tag}`, §6.3) and always call `showNotification(title, {body, tag, data: {url}, icon: "/icons/icon-192.png", badge: "/icons/badge-72.png"})`. A push that shows nothing gets the subscription revoked by Safari and counts against us in Chrome, so an invalid payload still shows "Terpsicle: open the app for details".
- `notificationclick`: close it, then focus an open window and navigate it to `data.url`, or `clients.openWindow(data.url)`. Only same-origin paths starting with `/` are opened.
- `pushsubscriptionchange`: re-subscribe with the VAPID public key and `POST /api/push/subscribe` (same-origin `fetch` from the service worker carries the session cookie).

Registration stays production-only, plus `localhost` when `VITE_SW_DEV=1` for push work. Previews don't register it.

Updates: a new version waits (no `skipWaiting` on install). Open tabs show a quiet "Update ready" toast with Reload, which asks it to take over and reloads; otherwise it takes over once every tab is closed.

### 3.3 Push subscription

- **One per device.** The browser has one subscription per service worker registration, and `push_subscriptions.endpoint` is unique. Subscribing upserts by endpoint, so if a second account signs in on the same device the row moves to that account and the first account's notifications stop reaching it. Signing out deletes the device's row (the sign-out request carries the endpoint).
- **Asking for permission** happens only on a person's own tap: a channel toggle in `/settings/notifications`, or Turn on in the ask at a moment (§6.7, "Asking"). Never on load.
- **iOS** allows web push only for a Home Screen app (iOS 16.4+). In a Safari tab the toggle shows "On iPhone, add Terpsicle to your Home Screen first: Share, then Add to Home Screen." with an "Add to Home Screen" link that opens the install dialog (§3.4).

### 3.4 The install prompt (`src/features/pwa/`)

A dialog after key moments that explains the benefits. It's allowed by the owner's decision; it isn't a confirmation dialog, and it's never a banner.

- **Triggers** (`requestInstallPrompt(trigger)`):
  - `first-sign-in`: after the first successful sign-in on this device;
  - `chat-joined`: the first time you open one of your chat rooms;
  - `alert-on`: the first time you turn on a seat alert.
- **Never shown when:**
  - already installed: `matchMedia("(display-mode: standalone)").matches` or `navigator.standalone`;
  - the platform can't install: no `beforeinstallprompt` captured on Chromium, and not iOS/iPadOS Safari (Firefox desktop, for example);
  - it was shown earlier in this session;
  - it was dismissed less than **90 days** ago, or twice in total (then never again, except from the menu item below).
- **Content:** title "Put Terpsicle on your home screen", then three lines: "Get notified when a seat opens or a classmate replies", "Open it from your home screen, like an app", "Use the full screen, without browser bars". Buttons: **Install** and **Not now**.
  - **Android and desktop Chromium:** `beforeinstallprompt` is captured at startup (`preventDefault()`, kept), and **Install** calls its `prompt()`.
  - **iOS and iPadOS Safari:** the dialog shows the steps instead of an Install button: 1 tap Share (with the icon), 2 "Add to Home Screen", 3 open Terpsicle from your Home Screen. One button: **Got it**.
- **Always available, quietly:** "Install app" in the account menu and in `/settings/notifications`, which opens the same dialog regardless of cooldown.
- **State:** `localStorage["terpsicle:install-prompt"]` = `{dismissals, lastDismissedAt}`, read with try/catch and a zod schema; storage failures mean "don't show". "Shown this session" is `sessionStorage["terpsicle:install-shown"]`. Every close without installing counts as a dismissal (Not now, Got it, Esc, declining the browser's prompt), except when the menu item opened it.
- `appinstalled` → the analytics event `pwa_installed`.

## 4. Identity

### 4.1 Rules
- **Sign in with Google only.** No magic-link fallback, no passwords, no other providers.
- **UMD accounts only:** the ID token's `hd` must be exactly `terpmail.umd.edu` or `umd.edu`, and `email_verified` must be `true`. Google can't tell students from alumni or staff, so copy says "UMD account", never "student".
- **Real names:** we store Google's name, the email, and the directory ID (the email's local part). No picture (§4.5). Users are keyed on the directory ID, not on `sub`: the same person has a different `sub` in the TERPmail and UMD Gmail tenants.
- **`x@terpmail.umd.edu` and `x@umd.edu` are the same user** (`users.id = 'x'`). Both addresses are recorded, one per Google identity (`user_identities.email`), whichever the person signs in with.
- **The name always comes from Google** and refreshes at every sign-in. There's no editing in Terpsicle; `/settings` tells people to change it in their Google account.
- **The scheduler works fully signed out.** Signing in adds plan sync; Chat, writing reviews and seat alerts need it.
- **The front door** (top bar button tooltip, the Chat page signed out, the sign-in sheet): "Sign in to join your class chats. Your plans sync too." Sign-in is invited, never required, for the scheduler.
- **Session:** a cookie on terpsicle.com, set only at sign-in and removed at sign-out. Signed out, terpsicle.com sets no cookie at all.

### 4.2 The Google OIDC flow (`src/server/auth/google.ts`, pure checks in `src/core/auth`)

No OAuth library (the research found the common ones deprecated). Plain `fetch` and WebCrypto.

**`GET /api/auth/google?return=<path>`**
1. Refuse unless `SIGN_IN_ENABLED` is `"true"` (redirect to `/signin?error=unavailable`). Rate-limit per IP.
2. `return` must be a same-origin path: starts with `/`, not `//`, no backslash, at most 512 characters; otherwise `/schedule`.
3. The redirect URI is `<origin>/api/auth/google/callback`, where the origin must be one of `GOOGLE_REDIRECT_ORIGINS` (a var: `https://terpsicle.com` in production; in `.dev.vars`, the localhost origin the owner registered, which `pnpm dev` serves on port 3000). These are exactly the redirect URIs registered with Google. Any other host gets 404.
4. Make `state` (32 random bytes), `nonce` (32 random bytes) and a PKCE `code_verifier` (32 random bytes, base64url), and `code_challenge = base64url(SHA-256(verifier))`.
5. Set `__Host-oauth` = `base64url(JSON {state, nonce, verifier, return, exp: now + 10 min})` + `.` + `base64url(HMAC-SHA-256(AUTH_SECRET, payload))`, with `Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=600`. Lax is needed: the callback is a top-level GET from accounts.google.com.
6. `302` to `https://accounts.google.com/o/oauth2/v2/auth` with `client_id`, `redirect_uri`, `response_type=code`, `scope=openid email profile`, `state`, `nonce`, `code_challenge`, `code_challenge_method=S256`, `prompt=select_account` and `hd=*` (the owner's choice: the account chooser favors Workspace accounts; it's only a hint, and the server checks `hd` itself in step 5 of the callback).

**`GET /api/auth/google/callback?code&state`** (or `?error=…`)
1. Read and verify `__Host-oauth` (signature, `exp`), then clear it. Missing or bad → `/signin?error=expired`. `error=access_denied` → `/signin?error=cancelled`.
2. `state` must equal the cookie's, compared in constant time.
3. `POST https://oauth2.googleapis.com/token` (form-encoded): `code`, `client_id`, `client_secret`, `redirect_uri`, `grant_type=authorization_code`, `code_verifier`. Non-2xx → `/signin?error=google-error`.
4. Decode the `id_token` payload and validate it with `GoogleIdClaimsSchema`. No JWKS check: the token came straight from Google's token endpoint over TLS, authenticated with our client secret, which Google documents as sufficient.
5. **Claim checks**, all in `checkGoogleClaims(claims, {clientId, nonce, now})` in `src/core/auth/claims.ts`, each with a test:

   | Claim | Rule | Error code |
   |---|---|---|
   | `iss` | `https://accounts.google.com` or `accounts.google.com` | `google-error` |
   | `aud` | equals `GOOGLE_CLIENT_ID` | `google-error` |
   | `exp`, `iat` | `exp > now − 60 s`; `iat < now + 300 s` | `expired` |
   | `nonce` | equals the flow cookie's | `expired` |
   | `hd` | present and exactly `terpmail.umd.edu` or `umd.edu` | missing: `personal-account`; other: `other-domain` |
   | `email_verified` | `=== true` | `unverified-email` |
   | `email` | lowercased; its domain equals `hd` | `other-domain` |
   | local part | matches `^[a-z0-9]{2,16}$` after lowercasing; this is the directory ID | `other-domain` |
   | `name` | optional; falls back to `given_name family_name`, then to the directory ID (`picture` is ignored, §4.5) | — |

6. Upsert the user by directory ID and the identity by `sub` (§4.4), refreshing `name`, `email` (the one just used) and the identity's `email`. If the user was `deleting` (within the 7-day grace, §4.7), signing in cancels the deletion.
7. Mint a session (§4.3), set the cookie, and `303` to `return` with `?signed-in=1` (the app strips it, runs the first-sign-in merge and the `first-sign-in` install trigger).

Sign-in errors land on `/signin?error=<code>&return=…` with plain copy:
- `personal-account`: "That's a personal Google account. Choose your @terpmail.umd.edu or @umd.edu account."
- `other-domain`: "Terpsicle is for UMD accounts. Choose your @terpmail.umd.edu or @umd.edu account."
- `unverified-email`: "Google hasn't verified that email address yet. Try again once it's verified."
- `cancelled`: "You cancelled signing in. Your plans are still here."
- `expired`: "That sign-in took too long. Try again."
- `google-error` / `unavailable`: "Google didn't finish signing you in. Try again in a minute." (the second when the flag is off: "Signing in is turned off right now.")
- If UMD's Workspace settings block the app, Google shows its own error before our callback; `/privacy` and the sign-in sheet say "If Google says your organization blocked Terpsicle, UMD's Google settings stopped it."

### 4.3 Sessions (`src/server/auth/session.ts`)

- **Cookie:** `__Host-session=<token>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=2592000`. The token is 32 random bytes, base64url. Only `SHA-256(token)` (hex) is stored.
- **Sliding 30 days, with a new token:** when `POST /api/me` or a route with `auth` sees a session whose `last_seen_at` is more than 24 h old, it mints a fresh session (`expires_at = now + 30 d`) and re-sets the cookie; the old row's `expires_at` drops to a minute from now, so a tab racing this one isn't signed out. A compare-and-swap on `last_seen_at` makes one request win. At most one write a day per session.
- **A fresh token at every sign-in** (no session fixation). Sign-out deletes the row and sends the cookie with `Max-Age=0`.
- **Lookup:** `getSession(request, env, now)` → `{user, sessionId} | null`, joining `users` with `status = 'active'`. The API route table declares `auth: "none" | "user" | "admin"` per route (§12); nothing else reads the cookie.
- **Local dev:** browsers accept `Secure` cookies on `http://localhost`, so the name and attributes are the same everywhere.
- The daily job deletes expired sessions.

### 4.4 Tables (migration `0003_identity.sql`)

```sql
-- One row per person, keyed on the UMD directory ID (the email's local part).
CREATE TABLE users (
  id               TEXT PRIMARY KEY,            -- directory ID, lowercase: 'jdoe'
  email            TEXT NOT NULL,               -- lowercase, the address used at the last sign-in
  hd               TEXT NOT NULL CHECK (hd IN ('terpmail.umd.edu', 'umd.edu')),
  name             TEXT NOT NULL,               -- Google's name, refreshed at every sign-in
  status           TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'deleting')),
  delete_after     TEXT,                        -- set while 'deleting' (§4.7)
  chat_blocked_until    TEXT,                   -- admin: no posting in Chat until then
  reviews_blocked_until TEXT,                   -- admin: no writing reviews until then
  created_at       TEXT NOT NULL,
  last_sign_in_at  TEXT NOT NULL
);
```

### 4.6 How PR previews sign in: a fixed test mode

Google forbids wildcard redirect URIs, and previews live at `pr-<n>-terpsicle.zsrobinson.workers.dev`. **Previews use a fixed test mode, not the real Google flow.**

- `AUTH_TEST_MODE: "true"` is set in `wrangler.jsonc`'s `previews.vars`, and by `vite.config.ts` for `pnpm dev:mock` (and so e2e). It's never set in production vars.
- Test mode is on only when `AUTH_TEST_MODE === "true"` **and** the host is a PR preview (`pr-<n>-terpsicle.zsrobinson.workers.dev`) or localhost, so never `terpsicle.com` or `www.terpsicle.com`, whatever the vars say. A worker test asserts that the top-level `vars` in `wrangler.jsonc` don't set it.
- `/auth/test` lists the fixture identities from `src/fixtures/users.ts` (`TEST_USERS`: `tstudent` "Test Student", `tclassmate` "Test Classmate", `tadmin` "Test Admin"), each with "Sign in as …". The button `POST`s `/api/auth/test-sign-in {userId, return}`, which upserts that user and mints a normal session. Everything after sign-in (sessions, sync, chat, reviews) runs the real code.
- In test mode, and only there, the fixture user `tadmin` is an admin (`TEST_USERS` marks it). The Google button shows "Sign in (test mode)" and goes to `/auth/test`.

**Why not a broker on terpsicle.com** (the callback lands on terpsicle.com and hands a one-time code back to the preview):
1. **Previews run unreviewed code.** A broker would give real Google identities (names, emails, pictures) to any PR's code, and would add a production endpoint that trusts `*.workers.dev` origins.
2. **Previews have their own D1** (`terpsicle-preview`), so a code minted in production D1 would need a server-to-server redemption API with a shared secret on both sides: more production surface for a test convenience.
3. **CI and e2e need a deterministic sign-in anyway.** Google can't be driven headlessly in CI, so test mode would exist regardless; a broker would be a second mechanism.
4. **What test mode doesn't cover is small and tested elsewhere:** claim checks are pure and unit-tested with real-shaped claims; the redirect is exercised on localhost (the owner registered a localhost callback) and in production. The deploy smoke check asserts `GET /api/auth/google` answers `302` to `accounts.google.com` with the right `client_id`, `redirect_uri`, `scope` and `code_challenge_method`.

### 4.7 Sign-out and account deletion

- **Sign out** (`POST /api/auth/sign-out {removeLocal, pushEndpoint}`): deletes the session and this device's push subscription, clears the cookie. Plans stay on the device and stop syncing. The menu offers two items: "Sign out" (tooltip "Your plans stay on this device") and "Sign out and remove plans from this device" (for a shared computer), which also clears Dexie's plans, blocks, colors, sync state and the `terpsicle:returning` flag.
- **The next sign-in on a device** merges whatever is local into that account, the same as a first sign-in (§5.4). That's why shared computers get the "remove plans" option.
- **Delete the account** (`POST /api/account/delete`): no dialog. It sets `status = 'deleting'` and `delete_after = now + 7 d`, deletes every session and push subscription, and signs out. The page says "Your account will be deleted on Oct 3. Sign in before then to keep it." Undo in the toast signs you back in through Google. The daily job purges accounts past `delete_after`:
  - `users` row (cascades: identities, sessions, sync rows, watches, settings, notifications, chat membership tables);
  - reviews stay published with `author_id` set to null ("Your published reviews stay up, with no name on them. Delete them first if you want them gone.");
  - chat messages: the purge calls `purgeAuthor(userId)` on each course object listed in `chat_author_courses` (§8.5), which deletes that author's messages;
  - As built (`v2/account-delete`, `src/server/auth/purge.ts`): the steps run chat, then one D1 batch (there were pictures in R2 between them until 2026-09-28, §4.5), and each is safe to repeat, so a run that dies midway is finished the next day. `purgeAuthor` also takes the person's reactions and send log, closes their sockets, tells the room the shown messages are gone, and withdraws waiting moderation items for them. Rows are deleted explicitly as well as by cascade: sync docs and heads, chat membership, follows, read markers and prefs, seat watches and seat alert sends, Todo's feed, items and done marks, sessions, identities, and `user:<id>:…` rate-limit counters. Every statement holds only while the account is still due, and the chat step checks before each object, so someone who signs in while a run is under way keeps their account. Reports stay for moderation with `reporter_id` swapped for a random `purged:` stand-in, and feedback stays for the owner with `user_id` null. `PURGE_LEDGER` names every table, and a worker test fails when a migration adds one it doesn't list.
  - Signing in during the week cancels the deletion, and the app says so quietly ("Your account is staying", from `?signed-in=kept`).

### 4.8 Admin

### 4.9 `POST /api/me`

Called on every app load. It never sets a cookie for a signed-out visitor.

The app's copy of the answer is one TanStack Query query (`meQuery`, `src/features/auth/me-query.ts`, `v3/query-me`) in the page's client: asked once per page by `AccountBoot`, and again only when something says the account changed (another tab's sign-out, sync's 401). ## 5. Plan sync

### 5.1 Model

- **Encrypted on the server with a key per account, never end-to-end** (the owner, 2026-10-04, `docs/decisions.md`; it settles §14's flagged "plain server-side storage"). Each account's data key is made by its first save, kept in R2 (`USER_KEYS`, apart from D1 so a database restore can't bring it back) wrapped by the Worker secret `USER_DATA_KEY`, and every doc's body is sealed with it, bound to its row (DATA.md §7.7). The Worker still opens bodies when it needs them, which is what lets Chat derive your rooms from your plan and the calendar feed read it, and keeps recovery simple: there are no sync keys, passkeys or recovery codes. Deleting the account deletes what the key sealed, then the key (the purge's step 2), so nothing it sealed opens again, even from a backup of D1. As built in `v2/sync-encryption`.
- **Deliberately not a sync engine.** The unit of sync is a **document**, saved whole with the server `rev` it was based on (compare-and-swap). Plans are never merged field by field. One person usually uses one device at a time, so conflicts are rare, and when one happens the person sees both versions.
- **Dexie stays the source of truth on each device.** The scheduler works offline and signed out exactly as today; sync copies docs up and down.
- **Docs** (`src/core/schema/sync.ts`; mapping to and from the Dexie tables in `src/core/sync/docs.ts`):
  - a **plan doc** per plan: the `Plan` row itself (term, name, tab order, courses with their sections, snapshots and saved-for-later entries, and since 2026-09-28 `registered`, the sections marked Registered in the Register tab: optional, absent in older docs; a difference in it counts as different work in a conflict);
  - one **settings doc** per user for what no single plan owns: blocks (per term, shared by the term's plans, DATA.md §5), course colors (global), travel settings, `mainPlans` (each term's main plan, §5.5; `chatPlans` before 2026-09-28, still written beside it for older builds), and `prefs`, the other products' prefs: `ai` (AI features, SPEC §3.13) and `chatRules` (the courses whose room rules you've closed, §8.6). `prefs` is loose (`SyncedPrefsSchema`): a key a build doesn't know rides along untouched, so a product can add one without the scheduler dropping it. As built (`v2/ai-opt-out`): on the device it's the `prefs` settings row plus a localStorage copy every page reads; Settings, Reviews and Chat write the row, mark the settings doc unsaved in the same transaction, and run the engine themselves while signed in (with no store: `src/features/prefs/account-sync.ts`), unless the scheduler's or Plan's is already running. Since `v3/todo-calendar` it also holds `todo` (Todo's week start). **A change made signed in before the engine's first step on the page** is made again once that step is done (`settleAccountPrefs`): on a device's first sign-in the step joins the account, which keeps the account's value for every key both sides have and would otherwise undo it; made again, it's marked unsaved and pushed.
- **Not synced:** UI prefs (tab, sidebar, theme, open drill-in), `activePlanByTerm` (the open tab: which plan is *main* is synced, which one is *open* isn't), generate drafts, the data cache. Seat watches are server-side already (§6.5).
- **Signing in turns sync on.** There's no separate toggle, and grades sync with the four-year doc (the owner, 2026-10-04).

### 5.2 D1 (migration `0005_sync.sql`, landed)

```sql
CREATE TABLE sync_docs (
  user_id    TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  kind       TEXT NOT NULL CHECK (kind IN ('plan', 'settings')),
  doc_id     TEXT NOT NULL,                     -- plan: its LocalId; settings: 'settings'
  term_id    TEXT,                              -- plans (a tombstone keeps its plan's); NULL for settings
  rev        INTEGER NOT NULL CHECK (rev >= 1), -- sync_heads.head at the save
  deleted    INTEGER NOT NULL DEFAULT 0 CHECK (deleted IN (0, 1)),
  body       TEXT,                              -- JSON (PlanDocSchema / SettingsDocSchema); NULL when deleted
  updated_at TEXT NOT NULL,                     -- server time of the save
  PRIMARY KEY (user_id, kind, doc_id),
  CHECK ((deleted = 1) = (body IS NULL)),
  CHECK (kind = 'plan' OR deleted = 0)
);
CREATE UNIQUE INDEX sync_docs_since ON sync_docs (user_id, rev);
CREATE INDEX sync_docs_tombstones ON sync_docs (updated_at) WHERE deleted = 1;

CREATE TABLE sync_heads (
  user_id        TEXT PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
  head           INTEGER NOT NULL DEFAULT 0,  -- the latest rev handed out
  pruned_through INTEGER NOT NULL DEFAULT 0   -- tombstones with rev <= this may be gone
);
```

One JSON row per doc, its body sealed since `0025_sync_encryption` (DATA.md §7.7: R2 `USER_KEYS` holds each account's wrapped key, and only `src/server/sync/store.ts` touches `sync_docs`). Revs come from the user's counter, so "every doc with `rev` > n" is a pull cursor, and no two of a user's docs share one. A tombstone is `deleted = 1` with a null body (the explicit flag keeps the plan cap and the pruning index simple); only plans have them. Bodies are validated with `SyncDocSchema`'s body schemas, and a plan body's `id` must be its `doc_id`. Limits (`src/core/schema/sync-api.ts`): a body ≤ 64 KiB of JSON, ≤ 200 live plan docs per user (tombstones don't count), ≤ 50 docs per push. Tombstones are pruned **30 days** after `updated_at` by the daily job, which raises `pruned_through` in the same batch. The account purge deletes a user's `sync_docs` and `sync_heads` rows along with the rest.

### 5.3 The API (`src/server/sync/`, `auth: "user"`)

- **`POST /api/sync/push`** `{docs: [{kind, id, baseRev, body | null}]}` (null = delete a plan; the settings doc can't be deleted) → `{results: [{kind, id, status: "ok", rev} | {kind, id, status: "conflict", doc: SyncDoc | null} | {kind, id, status: "too-many-plans"}]}`, in the push's order.
  - Each doc is saved only if its stored `rev` equals `baseRev` (0 = "new", no row). The whole push is one D1 batch, which runs as a transaction: per doc, a read of the stored row, a conditional `head + 1`, and a conditional upsert at that rev. So of two pushes on the same base, exactly one wins.
  - Docs are independent; a conflict on one doesn't stop the others. A conflict returns the server's current doc for §5.4, or `doc: null` when nothing is stored under that id any more (a tombstone pruned after 30 days): the device treats that as a delete and saves again on rev 0.
  - `too-many-plans`: the doc would be a new live plan past the 200 cap. Nothing is saved and no rev is used.
  - The request may be up to 51 × 64 KiB (every other route stays at 16 KiB).
- **`POST /api/sync/pull`** `{since}` → `{status: "ok", cursor, docs: SyncDoc[], more}` (rev > `since`, ascending, tombstones included, ≤ 200 per page; `cursor` is the page's last rev, or `since` when it's empty) or `{status: "reset"}`. A reset means the cursor can't be continued and the device pulls from 0 and treats it like a first sign-in (§5.4). That happens when `0 < since < pruned_through` (a tombstone it hadn't seen is gone) or `since > head` (the account was deleted and made again, so its revs started over). A device at 0 is never reset.
- **Chat membership is derived server-side from the stored docs:** a push that saves a plan doc or the settings doc rewrites that user's `chat_members` for the affected terms (§8.2). As built (`v2/chat-do`): right after the push's batch, from the docs actually stored, and the write is skipped if another save moved the user's `head` meanwhile (that push rewrites the rows itself), so a slow push never leaves stale rows. `term_id` on each row (kept on tombstones) is there for it (DATA.md §7.9).

**The device** (landed with `v2/sync-engine`: `src/features/sync/engine.ts`; flags from `planSyncReducer` in `src/core/sync/state.ts`):
- **No op log.** Each doc has a `rev` (0 = never saved) and a `dirty` flag, plus `inFlight` while a push is out. An edit marks the docs it changed dirty (`changedDocKeys`), in the same write queue as the edit itself, so the flag never lands before the doc; applying a server doc never does. A plan the app made on its own (a default name, no courses) isn't pushed until it's touched, and one never saved and then deleted needs no tombstone.
- push: the latest state of every dirty doc, 1 s after a change and when back online, in pushes of up to 50 docs;
- pull: on load, on `visibilitychange` to visible and window focus, and every 60 s while visible, page by page. A pulled doc replaces the device's version only when that doc isn't dirty or in flight; a dirty one is left for its push, whose compare-and-swap reports the conflict. When the account's plans arrive in a term, an untouched plan the app made there on its own goes.
- **A `reset`** runs the first sign-in's union (§5.4), except that docs this device holds unchanged since it last synced take the account's version first, so only real edits can turn into copies.
- **Failures:** no network (or `navigator.onLine` false) waits and retries 2 s, 4 s, … up to 60 s apart, and at once on `online` or when the tab comes back; `rate-limited` waits `retryAfterSeconds`; a 401 stops the engine, forgets the sync state and asks `/api/me` again. `too-many-plans` keeps the new plan on the device and says the account is full until the plan changes.
- **Tabs:** every step runs under one Web Lock (`terpsicle:sync`) and reads the flags from IndexedDB inside it, so two tabs never push the same change; docs in flight are sent again only by the next lock holder (a page closed mid-push). Tabs tell each other which docs they changed from the account over a `BroadcastChannel`, and reload them.
- **Undo:** a doc from the account is applied to every step of the undo history too (`rebaseHistory`), so undo never brings back what it replaced, and steps that only touched it disappear.
- **Loading:** the engine is a lazy chunk the scheduler loads once `/api/me` says someone is signed in; the scheduler hands it the store, the database and the rest (`SyncHost`), so it imports none of the scheduler's modules and signed-out visitors download none of it. Only the status store and its icon are eager.
- **Status**, quietly (DESIGN §5): the bar's sync slot (desktop: a cloud, then a word from 1280px: "Saved", "Saving…", "Saves when online", "Not saved yet", "Account full") and a line in the account menu: "Saved", "Saving…", "Offline, will save when you're back", "Couldn't save yet, trying again", "Account full", each with a tooltip. Pressing the icon checks with the account now.
- **Dexie v2** (`LOCAL_DB_VERSION` 1 → 2, with an `upgrade()`): a `syncDocs` table keyed by doc key (`plan:<id>` or `settings`): `{key, rev, dirty, inFlight}` (in-flight docs are made dirty again by the next step); the settings doc's `base` (its body as last saved or pulled, for §5.4) on its row; a `sync` settings row `{userId, cursor}`; a `chatPlans` settings row (`mainPlans` since Dexie v6, §5.5). The `seatAlerts` table is dropped; its rows move to a `seatAlerts` settings row until §6.5 retires the email-token flow.
- **The first sign-in toast** says what happened: "Your 2 plans are saved to your account", "Plan A was kept as Plan A (copy). Your account already had one by that name.", "Your changes are kept as Plan A (copy)" after a conflict. No dialogs.
- **Sign-out** (§4.7): both options stop the engine and forget the sync state (also via a `terpsicle:sync-reset` flag the next start reads, in case the page closes first). "Sign out and remove plans from this device" first pushes everything (joining the account if this device never synced); if something can't reach the account (offline), nothing is removed, the person stays signed in, and the menu says why. Then it clears the device and goes to `/`.
- **Tests:** `src/features/sync/engine.test.ts` runs the engine against `FakeSyncServer` (`src/fixtures/sync-server.ts`), and `src/server/sync/fake-server.test.ts` checks the fake answers exactly as the Worker does over D1, scripted and on random sequences from three devices. `e2e/sync.spec.ts` runs two browser contexts as one person in test mode, as throwaway `e2e…` users (`findTestUser`, test mode only) so tests never share an account.

### 5.4 Conflicts, undo and the first sign-in (`src/core/sync/`, pure, property-tested)

- **A plan doc conflict** (the server's rev moved): nothing is merged. The server's version stays as the plan, and this device's becomes a **new plan** named "<name> (copy)" ("(copy 2)", … on repeats; a copy of a copy counts on from the original name) at the end of the term's tabs. If both hold the same work (term, name and courses; tab order and timestamps don't count), the server's is simply taken. **An edit beats a delete** either way: a plan deleted elsewhere but edited here is saved again; one deleted here but edited elsewhere comes back.
- **A settings doc conflict:** it can't be kept twice, so it's settled per key (a block, a course's color, the travel settings, a term's main plan, one product's prefs). Keys this device changed since its `base` keep its value; every other key takes the server's; a key deleted on one side and edited on the other keeps the edit.
- **Undo stays local.** A server doc that replaces a plan becomes the new state, and that plan's undo history is cleared.
- **First sign-in on a device** (`firstSignInUnion`): pull everything, then upload every local plan the server doesn't have, after the account's tabs in its term. A local plan with the same term and name as a synced one gets "(copy)". A plan the account already has but that differs here (signed in before, edited while signed out) is kept both ways, as in a conflict. **Nothing is dropped**, with one exception: an untouched auto-created plan (a default "Plan X" name and no courses) isn't uploaded into a term where the account already has plans, or every new device would add an empty tab. The settings doc keeps the account's values for keys both sides have and adds what only this device has. A toast says "Your 3 plans are on your account now. Nothing was dropped."
- **Sign-out** keeps local plans unless the person picks "Sign out and remove plans from this device" (§4.7).

### 5.5 Main plans and term tags (owner-approved 2026-09-28, `v2/main-plan`)

Try as many plans as you like in Schedule; one of them per term, the **main plan**, is the one you're actually taking. Everything outside Schedule reads it; the rest are **drafts**, which only Schedule shows. The design canvas is in the orchestrator's scratchpad (`mainplan-design/`); `docs/decisions.md` has the decision.

- **Model** (`src/core/plans/main-plan.ts`, pure): `mainPlans: {[termId]: planId}` in the settings doc (so it syncs, and every device agrees; signed out it's this browser's `mainPlans` settings row). `mainPlanFor(termId, plans, mainPlans)` is the named plan while it's one of the term's plans, else the **first tab** (tab order: `order`, then `createdAt`, then id), so a term is never without one and the first plan of a term is main without anything being written.   - **Make main plan** (`plan/make-main`) names a plan, with an Undo toast: "Plan B is your main plan for Spring 2027" / "Chat, Plan, Todo and your calendar use it now."
  - **Deleting the main plan passes main to the next tab** (the one before when it was last; `mainPlansAfterDelete`), and the delete's toast says so: "Deleted Plan A" / "Plan B is your main plan for Spring 2027 now." Undo brings both back.
  - **Moving tabs never changes main:** a term going by its first tab names that plan before the move (`mainPlansBeforeMove`).
  - Duplicating the main plan makes a draft; opening a shared link never changes the main plan.
- **Older builds** called the same map `chatPlans` and can't read a settings doc without it. `SettingsDocSchema` reads `chatPlans` into `mainPlans` when a body has only that, and every push writes both (`settingsDocOf`, `mergeSettings`); nothing reads `chatPlans`. The server stores what it parsed, so a doc an older build pushes gets `mainPlans` too. No D1 migration: `chat_members` reads `$.mainPlans` of the doc a push just saved (§8.2). Drop `chatPlans` once those builds are gone.
- **In Schedule** (`src/features/schedule/plan-tabs.tsx`, `src/features/courses/main-plan-line.tsx`): with **two or more plans** in a term, the main plan's tab starts with a small square in Schedule's red (its description, for screen readers, is "Your main plan"), and the Courses and Register panels' titles say "Main plan" (red) or "Draft". A draft's Courses and Register panels open with one quiet line: "Your main plan for Spring 2027 is Plan A. Chat, Plan, Todo and your calendar use that one." and **Make Plan B main**. **With one plan, no mark and no words.** The tab's ▾ menu has **Make main plan** ("Chat, Plan, Todo and your calendar will use Plan B for Spring 2027."). Where only the open tab fits (phones), the other plans move into its ▾ menu ("Open Plan A") instead of a "+1" menu of their own, so its name keeps the room.
- **Everywhere else reads it:** Chat's rooms (§8.2, and its "Rooms from Plan A, your main plan ▾" menu makes another plan main everywhere, with Undo), Plan's "View schedule" and "From Plan A, main · 4 of 5 placed" (V3 §2.12), Todo's courses and "View schedule" (V3 §3.6), and the calendar feed (§6.7: `feedPlanFor` is the main plan).
- **Term tags** (`src/core/catalog/term-tag.ts`, the kit's `TermTag`): **Now** (an ink border) on the term in session and **Next** (a hairline) on the first fall or spring still to start, the one you register for, everywhere a term is named: Schedule's term button and menu, Chat's term, Plan's semesters and its phone strip, and Home's next-term heading ("Spring 2027 Next"). Worked out from the academic calendar with Plan's term spans (`termSpan`: first day of classes through grades), else the season's months, so every product agrees. Winter and summer are only ever Now; past terms stay under "Past terms" with Seats frozen. Schedule's term menu names each term's main plan ("Plan A, main · 3 plans", "Plan A · 5 courses", "No plans yet"). Below 1536px the bar says "Spring ’27" and a tagged term ends at its tag, so the plans' names keep their room.
- **Chat is only ever on Chat's term** (`chatTerm` in `src/core/catalog/term-tag.ts`, the owner 2026-09-29): of the terms Testudo lists, the one in session, else the next one to start (any season), since it's for the classes you're taking; Schedule stays on the term you're planning (usually Next). ### 6.1 Types × channels

Four types. "Not too many notifications for other things": don't add more. The one exception, approved by the owner, is v3's `todo-due` ("Due tomorrow", push only, at most one a day, off until ELMS is connected; `docs/V3.md` §4).

| Type | Push | Email | Default | Sent when |
|---|---|---|---|---|
| `seat-open` | ✓ | ✓ | push on, email on | A watched full section gets an open seat (§6.5). |
| `chat-mention` | ✓ | — | push on | Someone @-mentions you in a room you can read. |
| `chat-reply` | ✓ | — | push on | Someone replies to your message. |
| `chat-digest` | — | ✓ | off | Once a day, if you have unread mentions or replies from the last 24 h. |

- In a muted room, replies send no push; mentions still do (you were named).
- A person connected to that course's chat right now gets no push for it (they're looking).
- Moderation outcomes for your own review or message show in place (`/reviews/mine`, the held note in chat), never as a notification.
- The admin additionally gets an immediate email and push for an urgent moderation item (§9.4). That's an admin alert, not a user-settable type.

### 6.4 Web push with VAPID from Workers (`src/server/push/`)

No Node library; WebCrypto only, so it runs in the Worker and the Durable Object.
- **Keys:** a P-256 key pair. `VAPID_PUBLIC_KEY` (var, base64url uncompressed point, handed to the client in `/api/me`), `VAPID_PRIVATE_KEY` (secret, the JWK's `d`), `VAPID_SUBJECT` (var, `mailto:alerts@terpsicle.com`). `scripts/vapid-keys.ts` generates them.
- **VAPID (RFC 8292):** an ES256 JWT `{aud: <endpoint origin>, exp: now + 12 h, sub: VAPID_SUBJECT}`, signed with `crypto.subtle.sign({name: "ECDSA", hash: "SHA-256"})` (raw r‖s is what ES256 wants), sent as `Authorization: vapid t=<jwt>, k=<public key>`. JWTs are cached per push-service origin for an hour.
- **Payload encryption (RFC 8291, `Content-Encoding: aes128gcm`):** ephemeral ECDH P-256, HKDF-SHA-256, AES-128-GCM, one record. The unit test uses RFC 8291 Appendix A's example (fixed keys and salt) and must reproduce its ciphertext byte for byte.
- **Headers:** `TTL` (seat-open 3600; chat 86400), `Urgency` (seat-open `high`; chat `normal`), `Topic` for collapsing (a base64url hash ≤ 32 chars: per section for seat-open, per room for chat).
- **Payload** (`PushPayloadSchema`, ≤ 3 KB): `{v: 1, type, title, body, url, tag}`, e.g. `{type: "chat-reply", title: "Hannah Lee replied in CMSC131 · 0303", body: "check that you compare the names with .equals", url: "/chat/202701/CMSC131/section-0303?m=01J…", tag: "chat:202701:CMSC131:section-0303"}`.
- **Results:** 201 → `last_success_at`; 404/410 → delete the subscription; 429/5xx → `failure_count += 1`, delete after 10 consecutive failures; each send logs a `notification_deliveries` row.
- **Caps:** at most 30 chat pushes per user per hour (tags collapse the rest on the device anyway); seat-open keeps its alert caps (§6.5). (Superseded by §6.7: no caps on delivery.)
- `PUSH_ENABLED` (var) off → every push is `skipped`; previews have it off.

**As built** (`v2/push`; DATA.md §7.11):
- **Where:** its own page, `/settings/notifications` (`src/routes/settings_.notifications.tsx`, beside `/settings` rather than nested), linked from a Notifications row on `/settings`. Three parts: "What to send" (a row per type with its channel switches), "This device" (on or off here, the permission, the iOS note, "Turn on notifications on this device", "Turn off here", "Send me a test", "Install app") and "Devices with notifications on" (Remove with Undo; the server hears when the toast goes). Seat watches' Watching list stays on `/settings` (`v2/seat-watches`).
- **In the app** (`v3/query-notification-settings`): the settings and the devices are two TanStack Query queries (`notificationSettingsQuery`, `pushDevicesQuery`, `src/features/notifications/settings-queries.ts`, keys under `["notification-settings"]`, apart from the bell's `["notifications"]` so a read in the bell never asks for them again), a minute fresh, `retryApi` on network failures, and never paused offline, so a failed load says so with Try again. A switch is a mutation (`saveSettingsMutation`) that shows the change in the same tick and puts it back with "That didn't go through." by its group if the server doesn't take it, unless a later change already shows; saves send every setting, so they run one at a time in order (`scope`), and the settings are asked for again once the last has settled. Remove is a mutation (`removeDeviceMutation`) that stays pending through Undo's window, so the row is hidden from every list (over any refresh) until Undo, the toast going or the page closing (sent with `keepalive`); a failure brings the row back with a note. Turning on or off here, and a test, ask for the devices again. Signing out forgets both.
- **Rows:** seat openings (push and email), mentions in Chat, replies in Chat, the chat digest (email) and Due tomorrow. A row stays visible but quiet ("Coming soon") until its feature sends, which is `TYPE_ROWS[].sending` in `src/features/notifications/notification-settings.tsx`; the PR that makes a type send flips it. Seat openings send (below); mentions, replies and the digest since `v2/chat-notify` (§6.6).
- **Seat watches** (`notifySeatChanges`, `src/server/alerts/notify.ts`): on a reopen, push goes through `notify` (push only, key `seat-open:<user>:<term>:<section>:<asOf>`, so `…:push` in `notification_deliveries`), and the email keeps seat watches' own path (`seat_alert_sends`, `…:email`, the one-click stop) but only while `seatOpen.email` is on. The daily cap of 20 counts the busier channel. The push reads "A seat opened in CMSC351 0101" / "3 of 120 open. Register on Testudo before it's gone." and opens the course in the scheduler. Folding `seat_alert_sends` into `notification_deliveries`, and the email one-click turning off the channel rather than the watch, are left for later.
- **`notify(env, userId, {type, key, push, email?}, {now})`** (`src/server/notifications/notify.ts`) is the one way to notify: it reads the person's settings, pushes to each of their devices, emails when the type has email and an `email` is given, and records each channel in `notification_deliveries` under `<key>:push` / `<key>:email`, so a retried job sends nothing twice. It answers per channel: `sent`, `failed`, `skipped` (PUSH_ENABLED off, or no EMAIL binding), `off` (the person turned it off), `none` (no device, or no email given) or `duplicate`. Callers keep their own rules (seat watches' cooldown and cap, chat's muted rooms).
- **Routes** (all `auth: "user"`, per-person limits): `push/subscribe` (60/h; answers `ok`, `off` or `unsupported`), `push/unsubscribe` (60), `push/devices` (300; the endpoint never leaves the server, and passing this device's endpoint marks it `current`), `push/remove` by id (60), `push/test` (10), `notifications/settings` (300) and `notifications/settings/set` (120). `auth/sign-out` takes `pushEndpoint`; `account/delete` drops every device at once (signing back in to keep the account doesn't bring them back: turn notifications on again on each device); the purge deletes settings, devices and `notifications`, and blanks `notification_deliveries.user_id`. The daily job prunes deliveries after 90 days.
- **Only real push services:** the server POSTs wherever a saved endpoint points, so `isPushEndpoint` (`src/core/push`) takes https on FCM, WNS, Mozilla's and Apple's push hosts only; anything else is `unsupported`. A stored endpoint that stops passing is dropped on its next send.
- **Crypto** is `src/core/push`: RFC 8291 (its Appendix A reproduced byte for byte) and RFC 8292 (the RFC's example token verifies), WebCrypto only. JWTs are cached per push service and key for an hour; each message gets a fresh sender key and salt. A send never throws: 2xx → `last_success_at`, 404/410 → deleted, anything else (429, 5xx, a network error, a 10 s timeout) counts, and the 10th in a row deletes it.
- **"Send me a test"** pushes `{type: "test", title: "Notifications are on", body: "This is how Terpsicle reaches you on <device>.", url: "/settings/notifications", tag: "test"}` (TTL 300, `high`) to each device. It isn't a notification type: no settings, no delivery row. `PushTypeSchema` gains `test` and V3's `todo-due`, and the service worker's hand check follows.
- **Test mode** (previews, `pnpm dev:mock`, e2e) signs with a fixed VAPID pair (`TEST_VAPID_KEYS` in `src/server/push/config.ts`) and may send to `127.0.0.1` or `localhost`, where e2e's stand-in push service decrypts what it gets and hands it to the service worker. Mock mode sets `PUSH_ENABLED: "true"`; previews keep `"false"`. `/api/me` sends `pushPublicKey` and `flags.push` only while push works here (the flag and keys set).

The object resolves them against the room's members (`chat_members`, as `chat/members` lists them) each time a message becomes visible, so nothing about a mention is stored in the message and the `send` frame is unchanged. At most 5 per message over all its edits (an edit screened again can name someone new, up to the five), never the author. The composer offers the room's members after an "@" (loaded from `chat/members` the first time, you left out; that route's first 200 by name, so in a bigger room a later name is typed out in full, which still resolves), with arrows, Enter or Tab, a click and Esc; picking writes the full name. The list is hand-built like Generate's course field: Radix has no combobox.

- **Who hears** (`notifyChatMessage`, `src/server/chat/notify.ts`, rules in `chatRecipients`): once a message is visible (so a held one waits for its approval), one `notifications` row per person per message (a mention wins over a reply; an edit screened again adds nobody new but someone newly mentioned). A push goes through `notify` (after the room has the message, in `ctx.waitUntil`) unless the person has a socket open on the course's object that can read the room (they're looking), or it's a reply in a room they muted. (A cap of 30 chat pushes an hour went with §6.7: nothing caps delivery.) Reading the room up to the message sets `read_at`, as it clears the room's unread count: a thread's replies share the room's `seq`, so reading past one reads it, thread opened or not.

### 6.7 Delivery, redesigned (owner-approved 2026-09-27)

The same five types, delivered better: everything lands in an **inbox**, only what's urgent **pushes**, pushes **group** instead of piling up, one **badge** number means one thing, and dates go to a **calendar feed**. Design: the "Terpsicle notifications design" canvas and the "Terpsicle notifications: channels, iOS push and grouping" doc (both linked from the PR that added this section). The owner accepted the doc's defaults. This section is the contract the PRs below build against; each PR adds its "As built" here.

**Inbox (every type, signed in).**
- Every notification writes one inbox row, whether or not it pushes: seat openings, mentions, replies, "Due tomorrow" and, for admins, urgent moderation items. The existing `notifications` table grows to hold every type (new columns, one migration). D1 still never holds chat text: a chat row keeps its message reference, and the inbox reads the words from the course's object the way the digest does.
- Routes:
  - `notifications/inbox {before?: string}` answers `{items: InboxItem[], unread: number, next: string | null}`, newest first, 30 a page. `InboxItem` is `{id, type, product: "schedule"|"chat"|"todo"|"admin", title, body, url, count, createdAt, readAt}`. `count` is how many events the row stands for (a group).
  - `notifications/read {ids?: string[], all?: true}` answers `{unread}`.
  - `notifications/unread` answers `{unread}`, cheap, for the bar.
- Reading the thing itself marks its rows read, anywhere: opening the room (as today), the thread, the course in Schedule, or Todo's day.
- UI: a bell in the family bar with the unread count, opening the inbox: a popover on desktop, a sheet on phones, grouped by day, the kit's rows, "Mark all read", and a link to settings.

**Push, grouped.**
- Tags, one per group: `chat-mention:<roomId>`, `chat-reply:<threadRootId>`, `seat:<termId>` (every section that opened in one seats run is one push), `todo-due:<date>`, `admin-urgent`.
- The service worker keeps one notification per tag and rewrites it with a count ("3 mentions in CMSC351", "Seats opened in 3 sections you're watching", "4 replies to your question in CMSC351").
- Buzz again (`renotify`): a mention from someone new, a seat opening, and an admin item, yes; a reply, only the first in an hour; Due tomorrow, never.
- A click or a read closes the tag's notification.
- The payload gains `badge` (the unread count after this event) and `count`, still `{v, type, title, body, url, tag}` otherwise. iOS 18.4+ gets it as Declarative Web Push (`web_push: 8030`, `mutable: true`, so our service worker still groups where it runs).
- Titles, per the design: "Maya in CMSC351", "Maya replied to your question", "A seat opened in CMSC351 0101", "Project 2 is due tomorrow". No title starts with "Terpsicle".

**Badge.** `setAppBadge(unread)` from the push's `badge` and after every read in the app; `clearAppBadge()` at 0. It is the inbox's unread count, nothing else.

**When.**
- Quiet hours are on by default, 11pm to 8am New York. Pushes in them wait, and at 8am each group arrives as one push.
- Seat openings come through quiet hours by default (a seat can be gone by morning), with their own switch.
- **No caps on delivery.** The owner: "we should deliver all notifs if we say we have notifs so that it doesn't feel broken." There's no daily cap across types, and the 30-an-hour cap on chat pushes goes (today it drops pushes). A busy section chat stays calm through grouping instead: one notification per group, updated with its count, buzzing again only per the rules above. Seat openings keep their existing protections (the 30-minute cooldown per watch and 20 a day), which guard against a flapping seat count rather than volume.
- New settings keys: `quietHours: {on: boolean}` (default on), `seatThroughQuiet: boolean` (default true), `showText: boolean` (default true; off, a chat push reads "New mention in CMSC351").
- The settings page groups the switches by product (Schedule, Chat, Todo, then "When and how").

**Asking.**
- Permission is asked at three moments, in our words first:
  - turning on a seat watch (built);
  - after your first post in Chat;
  - after connecting ELMS in Todo.
- On iPhone outside the Home Screen, the ask is the three-step sheet (Share, Add to Home Screen, open it from there), and the app's first launch from the Home Screen shows the "Turn on notifications" step by itself.
- The install prompt's `first-sign-in` and `chat-joined` triggers get wired as §3.4 planned.

**Calendar feed.**
- One private, revocable link per person (`calendar_feeds`: the token's hash, created, last fetched), served at `/cal/<token>.ics` with no cookie. It holds:
  - this term's and next term's class meetings from each term's main plan (§5.5);
  - Todo deadlines (ELMS, file and own tasks, not done, not in a hidden course), each with a one-day-before alert.
- Settings has Add to Apple Calendar (`webcal://`), Add to Google Calendar, Copy the link, and Make a new link.

**As built (calendar feed, `v2/calendar-feed`).**
- **The link:** `calendar/feed` answers `{url, created}`, making the link on the first ask; `calendar/feed/reset` answers `{url}`. The token is an HMAC (`keyedHash`, the R2 key the one-click links use) of the person's id and a random nonce, 64 hex characters. D1 keeps the nonce and the token's SHA-256, never the token, so Settings shows the same link again without a copy of D1 being enough to make one, and a new link (a new nonce) matches nothing old. Table and limits: DATA.md §7.12.

## 7. Reviews (Terpsicle Reviews)

### 7.1 Rules
- **Anyone can read**, with no sign-in.
- **Writing and reporting require sign-in**, which proves a UMD account.
- **Anonymous to readers.** The backend stores the author (`reviews.author_id`), so people can edit and delete their reviews and limits work. **Nothing shown to readers, to the admin, or to moderation carries the author's identity** (§7.5).
- **Model-first moderation** (§9): clean reviews publish on their own; only uncertain or flagged ones reach the owner in `/admin`.
- **The scheduler** keeps, in course details: the numbers (rating, count, average GPA, grade bars) and each instructor's "Reviews" button, wearing Reviews' mark, which opens a preview (a popover; a sheet on phones): the rating, the grades sentence, the three newest reviews and "View reviews" → `/reviews/<id>?course=<code>` (owner, 2026-09-29). Full reviews and writing live at `/reviews` only. No AI summary (removed by the owner, 2026-09-29). (Since version A, §7.8: the header's rating and the whole preview are PlanetTerp's alone, credited "From PlanetTerp", and while our pages are off the preview leads to PlanetTerp instead.)
- **PlanetTerp ingestion stays** (hardened in #39). **PlanetTerp's reviews are shown** (owner, 2026-09-28), among ours, each marked with a "PlanetTerp" chip, no author (§7.7). The private `_jobs/planetterp/reviews/` copy kept for summaries was removed with them (2026-09-29).
- **Never edit a review's words.** We publish, hold or remove whole reviews.

### 7.2 Instructor ids

A review needs an instructor id that doesn't depend on PlanetTerp. The id is the PlanetTerp slug when the name join knows the instructor (so links keep working), else a minted `t~` + 10 base32 characters. `InstructorSlugSchema` must accept both (widen its pattern in the reviews PR).

### 7.3 D1 (migration `0008_reviews.sql`)

```sql
CREATE TABLE instructors (
  id               TEXT PRIMARY KEY,           -- PlanetTerp slug, or 't~' + 10 base32
  name             TEXT NOT NULL,              -- display name (Testudo's, else PlanetTerp's)
  planetterp_slug  TEXT UNIQUE,
  created_at       TEXT NOT NULL
);

-- Testudo name → instructor, per department; filled at first use (§7.4, submit).
CREATE TABLE instructor_names (
  name_key       TEXT NOT NULL,                -- instructorNameKey(testudoName)
  dept           TEXT NOT NULL,
  instructor_id  TEXT NOT NULL REFERENCES instructors (id),
  rule           TEXT NOT NULL CHECK (rule IN ('planetterp', 'minted', 'manual')),
  updated_at     TEXT NOT NULL,
  PRIMARY KEY (name_key, dept)
);

CREATE TABLE reviews (
  id             TEXT PRIMARY KEY,             -- 16 random bytes, base64url
  author_id      TEXT REFERENCES users (id) ON DELETE SET NULL,  -- null once the account is purged
  instructor_id  TEXT NOT NULL REFERENCES instructors (id),
  reviewed_name  TEXT NOT NULL,                -- the Testudo name on screen, so a wrong join can be moved
  course         TEXT NOT NULL,                -- CMSC351
  term_id        TEXT,                         -- when they took it; optional
  rating         INTEGER NOT NULL CHECK (rating BETWEEN 1 AND 5),
  grade          TEXT,                         -- A+ … F, W, P, or null ("Rather not say")
  body           TEXT NOT NULL,                -- 40–2,000 characters
  text_hash      TEXT NOT NULL,                -- normalized-text SHA-256, catches copies
  status         TEXT NOT NULL CHECK (status IN ('published', 'held', 'rejected', 'hidden', 'deleted')),
  reason         TEXT,                         -- moderation reason code, shown to the author in plain words
  pending_edit   TEXT,                         -- JSON {rating, grade, termId, body} waiting for a check
  report_count   INTEGER NOT NULL DEFAULT 0,
  created_at     TEXT NOT NULL,
  published_at   TEXT,
  edited_at      TEXT,
  updated_at     TEXT NOT NULL
);
CREATE UNIQUE INDEX reviews_one_per_course ON reviews (author_id, instructor_id, course)
  WHERE status IN ('published', 'held', 'hidden');
CREATE INDEX reviews_by_instructor ON reviews (instructor_id, status, published_at DESC);
CREATE INDEX reviews_by_course ON reviews (course, status, published_at DESC);
CREATE INDEX reviews_by_author ON reviews (author_id);
CREATE INDEX reviews_changed ON reviews (updated_at);
CREATE INDEX reviews_by_hash ON reviews (instructor_id, text_hash);
```

Reports live in the shared `reports` table (§9.3). Rejected text is blanked 30 days after the decision; deleted reviews are blanked at once and the row removed after 30 days.

### 7.4 API (`src/server/reviews/`, routes in `api-routes.ts`)

| Endpoint | Auth | Input → result |
|---|---|---|
| `reviews/list` | none | `{instructorId, course: code \| null, cursor, limit ≤ 20}` → `{reviews: PublicReview[], next}`; published only, newest first, `no-store` |
| `reviews/submit` | user | `{instructorId \| null, reviewedName, dept, course, termId \| null, rating, grade \| null, body}` → `{status: "published" \| "held" \| "rejected", reviewId, reason?}` (synchronous, ~4 s; the UI shows "Checking…") |
| `reviews/edit` | user, own | `{reviewId, rating, grade, termId, body}` → same union. A published review stays up with its old text while an edit waits. |
| `reviews/delete` | user, own | `{reviewId}` → `{status: "deleted"}`. The UI waits for its Undo toast (the app's 10 s window) before calling. |
| `reviews/mine` | user | `{}` → your reviews with status and reason |
| `reports/create` | user | `{surface: "review", ref: reviewId, reason, note \| null}` (shared with chat, §9.3) |

- `submit` resolves the instructor: the given id if it's valid; else the PlanetTerp `names` map for `dept`; else `instructor_names`; else it mints one. Stage-0 rules (§9.1) fail inline with specific copy ("Take out the link. Reviews can't include links.") and store nothing.
- **Limits:** one live review per (author, instructor, course) (a second becomes an edit of the first); 10 new reviews per author per 7 days; `users.reviews_blocked_until`; a burst hold (more than 5 new reviews for one instructor in 24 h, or 3× the 30-day average) sends the rest to the queue.
- `REVIEWS_ENABLED`: `off` (every route `unavailable`, the UI shows today's PlanetTerp-only view), `read` (list and numbers, no writing), `on`.
- `REVIEWS_PAGES_ENABLED`: `"true"` opens our `/reviews` pages; unset (production and previews since version A, §7.8) sends them to PlanetTerp and reads `REVIEWS_ENABLED=on` as `read`.

### 7.5 Anonymity rules
1. `PublicReviewSchema` is `{id, course, termId, rating, grade, body, createdMonth: "YYYY-MM", edited: boolean}`: no author field, no user-derived id, and the date rounded to the month to blunt timing guesses.
2. `author_id` never leaves `src/server/reviews/store.ts` except as a boolean ("is this yours") and for limits. Admin and moderation payloads (`AdminReviewItemSchema`) have no author field; a worker test asserts every admin and public payload is free of `author`, `userId`, directory IDs and emails.
3. Admin actions against an author go through the review id: "Stop this author writing reviews for 30 days" sets `reviews_blocked_until` without showing who.
4. No review id, instructor id or course code in analytics events about writing; no author id in logs.
5. `/reviews/policy` says it honestly: "We store which account wrote a review so you can edit or delete it and so limits work. We never show it to readers or moderators."

### 7.6 Merging with PlanetTerp data
- **R2 family `reviews/`** (served, written by the hourly `reviews-publish` job):
  - `reviews/manifest.json` (`ReviewsManifestSchema`: `{schemaVersion, generatedAt, departments: [{code, hash}]}`), `no-cache`, edge 1 h;
  - `reviews/dept/<DEPT>.<hash>.json` (`ReviewsDeptSchema`: per instructor id `{rating, reviewCount, latestReviewMonth}` from published Terpsicle reviews, plus `names` for minted instructors and the owner's `manual` fixes), hashed and immutable. The newest review is a month, not a time, by §7.5's rounding (`DATA.md` §4.6).
  - A new `SCHEMA_VERSIONS.reviews` family. Review **text** is never in R2 (hashed files are immutable for a year, and a removal must be instant); it comes only from `reviews/list`.
- **Combined numbers** (`combineRatings` in `src/core/reviews/combine.ts`, landed with `v2/reviews-ui`; until `v2/reviews-publish`, our side comes from `reviews/list`): `rating = Σ(rating_s × count_s) / Σ count_s` over PlanetTerp and Terpsicle; `reviewCount = Σ count_s`; the tooltip gives the parts ("4.2 from 61 reviews: 4.1 from 48 on PlanetTerp, 4.6 from 13 on Terpsicle"). Grade distributions stay PlanetTerp's; self-reported grades never mix in.
- **Summaries:** removed on 2026-09-29 (owner: "let's remove all AI features for reviews"), with `review-summary`, `src/server/summaries` and `SUMMARIES_DAILY_CAP`.
- **Copies:** stage 0 rejects text matching a published Terpsicle review of the same instructor ("This review is already posted."). Cross-posts from PlanetTerp can't be detected without its text; that's accepted.

## 8. Chat (Terpsicle Chat)

### 8.1 Rooms, derived (`src/core/chat/rooms.ts`)

Rooms come from the catalog with the grouping course details already uses (`src/core/catalog/section-groups.ts`). Nobody creates a room.

As built (#49, then the owner's one-level grouping, 2026-09-26): ids are `RoomId`s in `src/core/schema/chat.ts` (DATA.md §1).

```ts
// "202701:CMSC131", "202701:CMSC131:P:pedram-sadeghian", "202701:CMSC131:0303"
export function roomsForCourse(termId: TermId, course: Course): RoomTree;   // pure, cached per course
export function roomsForSection(tree: RoomTree, sectionCode: SectionCode): Room[];
export function myRooms(plan: Plan, index: CatalogIndex): Room[];
```

Rules (the owner, 2026-09-26: one level of grouping, like course details):
1. Every course has a course room ("CMSC131 · everyone"). With one section, that's the only room.
2. With two or more sections, every section gets a room.
3. With more than one professor, each named professor gets a room between the course and their sections ("Sadeghian's sections"). One professor: the course room is theirs. TBA sections sit right under the course room. **No lecture rooms:** section codes already say which sections share a lecture.
4. The room list groups like course details (`groupSectionsByInstructor`): by professor, sections sorted by code, with no heading when there's one professor; past `MANY_SECTIONS` (20), groups start collapsed and yours are pinned on top.
5. Section rooms are named by all their meetings ("0303 · MWF 11am and TuTh 11am discussion", "IRB 0324, CSI 1121").

Edge cases: labs name like discussions; a section with no set time still gets its room ("0101 · online, no set time"); a time or room change renames in place (history stays); a cancelled section's room turns read-only with one quiet line pointing to the course room; cross-listed codes get separate rooms.

### 8.2 Your rooms and who can read them

- **Your rooms come from your synced plan's sections.** Per term, they're your **main plan**'s (§5.5): the settings doc's `mainPlans` (`{[termId]: planId}`, §5.1), defaulting to the term's first tab. The chat list shows "Rooms from Plan A, your main plan ▾" (with two or more plans; "Rooms from Plan A, your Fall 2026 plan" with one), and picking another plan there makes it main everywhere, with Undo. Your rooms: for each course in that plan, its course room, plus the professor and section rooms of the placed section; for bookmarked courses, the course room only.
- **Course rooms are open** to any signed-in user, including people still deciding: course details has "Join CMSC351 chat", which adds a `chat_follows` row so it stays in your list.
- **Only Chat's term** (the owner, 2026-09-29: "you shouldn't be able to join one for a future course, that's confusing. your chat tab should just pull from the current semseter."). Chat's term is `chatTerm`: of the terms Testudo lists, the one in session (the one that started last when two overlap, as Now does), else the next one to start, winter and summer included; only listed terms, since rooms come from the catalog. The list, its rooms, the rooms from your main plan and the bar's term are all that term's, and there's no term menu. "Join … chat" in course details shows only for a course in Chat's term, and `chat/follow` answers `{status: "other-term"}` for any other term, saving nothing. A link to another term's chat opens the list. Follows and messages from before the rule, in a term still to come, are kept and hidden: they show once that term is Chat's.
- **The list shows only your rooms** (the owner, 2026-09-28): other sections' and professors' rooms aren't listed, locked or otherwise; to see one, you'd add that section to a plan. - **Names and links** (the owner, 2026-09-29; `src/core/chat/room-paths.ts`, the one place any of them is made): a room is **Everyone**, **Nelson's Sections** (the professor's last name) or **Section 0101**, under its course's code, and "CMSC351 · Section 0101" where nothing above names the course (notifications, the digest, the inbox, the composer). It powers member counts, @-mention autocomplete and "people in this room". It describes people, not rooms, so it doesn't break §8.3's rule.

### 8.3 Nothing is stored for a room until its first message

- Rooms are computed in the browser (catalog + synced plan) and in the object (catalog), never listed from storage.
- The `CourseChat` object for a course is only addressed when someone opens that course's chat; a Durable Object that never writes has no storage.
- The first message in a room creates its `rooms` row in the object and its `chat_rooms` row in D1. Before that, the room shows "No messages yet. Say hi to your classmates."
- Unread counts for the chat list come from one D1 query over `chat_rooms` and `chat_read_markers`, so opening `/chat` wakes no objects.

### 8.4 The `CourseChat` Durable Object

**As built (`v2/chat-do`; DATA.md §7.9 is the reference).** The object speaks core's protocol (`ChatClientFrameSchema` and `ChatServerFrameSchema` from #49), which supersedes the frame sketch below: `hello {protocol, rooms}` (sent again after a sync to recheck rooms, in place of `refresh`), `history` by message id with threads, `send`, `edit`, `delete`, `react`, `typing` and `read`; answers `welcome`, `page`, `ack`, `error`, `message`, `deleted`, `reactions`, `moderation` and `typing`. So reactions, typing and one-level threads ship in this release after all (core's schema has them), and the first-release list at the end of this section is down to pins, search, images and files, and per-course display names. Other differences from the sketch: statuses are `checking` · `visible` · `held` · `removed` (a hold only for a failed model call stays `checking`, as core's `held: checking`); mentions arrived with `v2/chat-notify` (§6.6 "As built"), resolved from the text rather than sent as a `mentions` field; authors come from `users` as they are now (AUTH.md), with our `/avatars/…` copy as the picture, not a snapshot; a send's `req` is its idempotency key (for `client_id`); `CHAT_ENABLED: "read"` answers sends with `read-only` (core has no `unavailable` code) and welcomes with `writable: false`; an admin block answers `slow-down` with the seconds left. `chat_rooms` also stores each room's `kind` and section codes, so `chat/unread` needs no catalog.

- **One object per course per term:** `env.COURSE_CHAT.idFromName("<termId>:<courseCode>")`, class `CourseChat` in `src/server/chat/course-chat.ts`, exported from `src/server.ts`. SQLite storage and the WebSocket Hibernation API (`ctx.acceptWebSocket`, `serializeAttachment`, `setWebSocketAutoResponse` for ping/pong). Why this size (the Chat canvas's architecture board): a course's rooms move together, one socket covers every room of a course, and even ENGL101 (93 rooms) or CMSC131 (~600 people) is far below one object's limits. One object per room would mean 93 objects and a reconnect per room switch; one per campus would put every message at UMD through one thread.
- **It reads the catalog** from R2 `DATA` (`catalog/<term>/manifest.json` → the course's department chunk) to build its `RoomTree` with `chatRooms`, cached in memory and refreshed when older than an hour.
- **It reads D1** (`DB`) for profiles, plan-based authorization, settings and push subscriptions, and writes `chat_rooms`, `chat_read_markers`, `chat_author_courses` and `notifications`.

**Object storage (SQLite inside the object):**

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);   -- term_id, course_code, read_only_at, delete_at
CREATE TABLE rooms (                                          -- a row only after the first message
  room_id      TEXT PRIMARY KEY,
  last_seq     INTEGER NOT NULL,
  created_at   TEXT NOT NULL
);
CREATE TABLE messages (
  id          TEXT PRIMARY KEY,         -- time-sortable, 26 chars (ULID), minted by the object
  room_id     TEXT NOT NULL,
  seq         INTEGER NOT NULL,         -- per room, from 1; clients resume from it
  author_id   TEXT NOT NULL,            -- users.id
  body        TEXT NOT NULL,            -- plain text, 1–2,000 characters
  reply_to    TEXT,                     -- a message id in the same room
  mentions    TEXT NOT NULL DEFAULT '[]', -- JSON array of user ids, ≤ 5
  status      TEXT NOT NULL CHECK (status IN ('pending', 'visible', 'held', 'removed')),
  labels      TEXT NOT NULL DEFAULT '[]', -- moderation labels
  client_id   TEXT NOT NULL,            -- sender's idempotency key
  created_at  TEXT NOT NULL,
  edited_at   TEXT,
  UNIQUE (author_id, client_id),
  UNIQUE (room_id, seq)
);
```

A message deleted by its author is deleted at once (row gone, a `deleted` event broadcast).

**`GET /api/chat/socket?term=<termId>&course=<code>`** (`Upgrade: websocket`). The Worker checks `CHAT_ENABLED` (not `off`), the session, `Origin` (§12), the rate limit, and that the term is known; then forwards to the object with `X-Terpsicle-User: <userId>` (the object is reachable only through the Worker, so it trusts that header). The socket's attachment holds `{userId, readableRooms, connectedAt}`.

**Protocol** (`src/core/schema/chat.ts`, JSON text frames, validated both ways):

```ts
// client → server
{ t: "hello", v: 1, since: Record<RoomId, number> }   // last seq seen per room; server replays after it (≤ 200 per room, else "gap")
{ t: "history", room: RoomId, before: number, limit: number }   // ≤ 50
{ t: "send", room: RoomId, clientId: string, body: string, replyTo: string | null, mentions: string[] }
{ t: "edit", id: string, body: string }
{ t: "delete", id: string }
{ t: "read", room: RoomId, seq: number }
{ t: "refresh" }                                     // after a sync: recheck which rooms you can read

// server → client
{ t: "ready", me: UserId, rooms: RoomState[], readOnly: boolean }        // RoomState: {room, lastSeq, unread, canPost, members}
{ t: "messages", room: RoomId, messages: ChatMessage[], gap: boolean }   // replay and history
{ t: "message", message: ChatMessage }                                   // new, edited, held (author only), removed
{ t: "deleted", room: RoomId, id: string }
{ t: "ack", clientId: string, id: string, status: "pending" | "visible" | "held" }
{ t: "profiles", users: { id: UserId, name: string }[] }
{ t: "error", code: "rate-limited" | "not-allowed" | "read-only" | "invalid" | "unavailable" | "blocked", clientId?: string, retryAfter?: number }
```

`ChatMessage` = `{id, room, seq, authorId, body, replyTo, mentions, status, createdAt, editedAt}`. Names travel separately in `profiles` (sent for authors the client hasn't seen), from D1 `users`.

**Sending:**
1. Validate (length, room readable, not read-only, not `chat_blocked_until`, limits: 10 messages per 30 s per user per course, 500 per day).
2. Record `chat_author_courses` on the author's first send in the course, before storing it, so account deletion reaches held messages too (as built in `v2/account-delete`). Store as `pending`; ack `pending` to the sender, who sees it at once in muted style. As built (`v2/chat-moderation-light`, the owner 2026-09-27): the sender sees it as sent, not muted and with no note; classmates get it when the check passes, usually within a second.
3. Screen with the moderation service (§9), surface `chat`. As built (`v2/chat-moderation-light`): first the cross-room spam guard (MODERATION.md §2), which may hold it for the owner, urgent, without a model. Allowed → `visible`, broadcast to sockets that can read the room; held → `held`, sent to the author only with the note (§9.2). A model error is retried by the moderation cron within 5 minutes before the message goes to the human queue (§9.2); the result reaches the object through Chat's handler.
4. Once visible: update `chat_rooms` in D1, and for each mention (a member of the course, not the author) and the replied-to author, insert a `notifications` row and, per their settings and if not connected here, send a push (`ctx.waitUntil`).

`CHAT_ENABLED: "read"` answers `send` with `unavailable` (reading works); `off` refuses sockets.

**Retention (DO alarms):**
- **Read-only** at the term's `classesEnd` + 10 days (from `calendar/<term>.json`), or when `terms.json` marks the term archived if the calendar isn't published. Rooms then show "This term's over. The rooms stay readable until Feb 19."
- **Deleted** 60 days after read-only: `ctx.storage.deleteAll()`, plus the D1 rows for that course and term (`chat_rooms`, `chat_read_markers`, `notifications`, `chat_author_courses`).
- The alarm is first set with the first message. Moderation snapshots of chat items are blanked 30 days after a decision (§9.4). There's no export at launch.

**Not in the first release:** reactions, pins, threads beyond one-level replies, search, images and files, typing indicators, per-course display names (Chat uses real Google names and initials, no pictures; no pseudonyms or anonymous posting).

A desktop fills the pane beside it; a phone (≤ 768px) slides the room in over the list, which stays mounted underneath so Back finds it where you were, and every control is 44px there.
- **A room keeps its shape from the first frame** (`v2/chat-calm`): its header, message-shaped bars at the bottom where the latest messages land, and the composer, which takes a send while the room connects (the session sends it after the welcome). The header's line under the name holds its height until the people count arrives, and the messages stick to the bottom through any resize (a note over the composer, a reaction, the phone's keyboard).
- **Your rooms come from your synced plans,** read with `sync/pull` (what the server checks), not the scheduler's local plans: `/chat` never loads the scheduler's stores up front. The read is a query (`chatSyncedQuery`) that each visit to Chat asks again, showing what it had meanwhile, and coming back to the tab after a minute too; the sync engine stays with Schedule and Plan. The terms, calendars and catalog come through the same published queries the other products read (`src/features/chat/chat-reads.ts`, loaded on first use; DATA.md §5.5), so a manifest is read once a page and shared with Schedule. A room's members (the "@" list, and course details' "Join CMSC351 chat · 42 people") are one query per room, current for 5 minutes (`roomMembersQuery`). "Rooms from Plan A, your main plan ▾" saves `mainPlans` (and its old name, `chatPlans`) in the settings doc with its rev, with an Undo toast that saves the old choice back; it shows only once a settings doc exists (the sync engine writes the first). Join, Leave and Mute are mutations (`src/features/chat/chat-mutations.ts`): each shows at once, comes back down if the server says no, and the counts are asked for again once it settles.
- **Author-only states:** "Sending…" (only after 2 s), and held (flagged, reported, and graded work for older messages) and removed, tinted yellow with a warn edge and one plain line from `heldWords` ("Held for review. Only you can see it until a person checks it.", `v2/chat-calm`); a refused send offers Try again and Discard. A message still being checked has no state at all: it looks sent (`v2/chat-moderation-light`; it said "Checking before classmates see it…" before). Reactions are the fixed five; threads are one level (a thread replaces the room view). Edit, delete and leave each get an Undo toast, one at a time; a delete is sent when its undo runs out.
- **Reporting** is inline on a message (a reason and an optional note); `reports/create` takes chat refs now (MODERATION.md §6). "Posting here" and What's allowed say how. As built (`v2/chat-moderation-light`): abuse only, "Harassment or hate", "A threat", "Sexual content", "Spam", "Someone's private info" and "Something else" (which needs a note). The form asks "Why are you reporting it?" and thanks with "Reported. A person will read it." (`v2/chat-calm`).
- **The composer** never says a message will be checked. Its one hint is a plain note, once per browser, when a draft looks like answers to graded work ("This reads like answers to graded work, and your name goes on it.", `v2/chat-calm`); the message still sends (`v2/chat-moderation-light`).
- **Signed out,** `/chat` says what Chat keeps and what classmates see before the Google button. "Posting here" shows once per course, and "Got it" (or a first post) follows the account, so a new device doesn't show them again (the settings doc's `prefs.chatRules`, §5.1).

- **The scheduler's way in:** course details has "Join CMSC351 chat · 42 people" (the course room's head count from `chat/members`) while Chat is on, loaded on demand so `/schedule`'s first load doesn't carry it; it follows the course and opens its room.
- **Anonymous chat is held off** (the owner, 2026-09-28): classmates liked the idea, but misuse is the worry. Everything carries your real name; nothing is built toward it (`docs/decisions.md`).

## 9. The shared moderation service

One service for reviews and chat: `src/server/moderation/` (Worker side), with the pure rules and policy in `src/core/moderation/`. **As shipped in #52; `docs/MODERATION.md` has the details** (rules, Guard categories, thresholds, config, the eval).

```ts
import { moderate } from "~/server/moderation";
await moderate(env, { kind: "review" | "chat", text, context: { targetId, course?, activeAssignments? } }, { now });
// → { decision: "publish" | "hold" | "remove", reasons: ModerationReason[], model: { guard, policy }, scores }
```

It always writes a `moderation_decisions` row and, for `hold`, a `moderation_queue` item. The tables use this section's words: `surface` = kind, `ref` = targetId; verdicts `allow` / `hold` / `reject`. It throws only on bad input or a D1 failure; model trouble is a hold. Later decisions (a retry that passes, the owner) reach the feature through its handler in `MODERATION_HANDLERS` (`src/server/moderation/handlers.ts`); `currentDecision(db, kind, targetId)` reads the state. Composers use `precheck()`, `REASON_WORDS`, `LENGTH_LIMITS` and `MODERATION_POLICY` from `~/core/moderation` for inline errors and "What's allowed". Tests mock the `AI` binding.

### 9.1 Stage 0: rules (`src/core/moderation/precheck.ts`, instant, pure)

Length (reviews 40–2,000, chat 1–2,000), a blocklist, links (only `umd.edu` and `terpsicle.com`; answer sites always held), contact details and UIDs (chat allows your own), and academic-integrity patterns (answer lists, "here are the answers", code pasted while `activeAssignments`). Each finding is a reason with an action (`flag`, `hold`, `remove`) and a span. A rule `remove` ends it without a model call. Table: MODERATION.md §3.

**As built for chat (`v2/chat-moderation-light`, the owner 2026-09-27):** chat's rules only act on slurs (remove), blocked words and UIDs that aren't your own (hold). Links, contact details (anyone's), insults, asking for answers and code are allowed; answer lists and answer sites only flag, for a one-time composer nudge. A short reply ("thanks!") or an emoji publishes without a model. Before the rules, chat's spam guard holds the same text in 3+ courses within an hour, or more than 12 messages across more than 4 courses in 10 minutes; one course's rooms count once (`chat_send_hashes`, migration `0014`).

### 9.2 Stage 1: Workers AI with Meta models

Both calls run in parallel through the `AI` binding, with the text fenced as untrusted data. A slow or failed attempt gets a second, racing one after 1 s; a stage gives up at 10 s.

- **Llama Guard 3** (`@cf/meta/llama-guard-3-8b`): `safe`, or `unsafe` with S1–S14, each mapped to flag, hold (S1, S3, S9, S11 urgent) or remove (S4).
- **A Llama instruct model** in JSON-schema mode scores each label from 0 to 1: `academic-integrity`, `targets-person`, `personal-info`, `spam`, and for reviews `misconduct-claim` and `off-topic`. Hold at 0.5 (off-topic 0.6); only spam and off-topic ≥ 0.9 remove.
  - Reviews: `@cf/meta/llama-3.3-70b-instruct-fp8-fast`, every label.
  - Chat: `@cf/meta/llama-3.1-8b-instruct-fp8-fast` (measured: p95 1.4 s end to end, no missed graded-work case; STATUS.md), on every message. When nothing flagged it, only `targets-person` acts. As built (`v2/chat-moderation-light`): chat scores only `targets-person` (hold 0.5), `personal-info` (hold 0.9, only with someone else's detail to expose) and `spam` (hold 0.9, never remove); `academic-integrity` no longer acts on chat. Measured live: 33 of 33 chat cases, p95 under 1 s.
- The decision is the most severe action; flags never hold on their own.
- **Model error, invalid output, or over `MODERATION_DAILY_CAP`:** hold as `retry`, which the owner doesn't see. The every-5-minutes cron (`src/jobs/moderation.ts`) screens it again within 5 minutes; it reaches the owner only on a real problem or after 2 failed retries. Reviews and chat alike.
- Thresholds, models, hedge and chat mode are constants with tests, overridable by the `MODERATION_CONFIG` JSON var.

Nothing publishes because it waited. What a held author sees, in plain words and never in red: reviews, "A person will look at this first. That usually takes a few days. You can edit it while it waits."; chat, "Only you can see this. It looks like it could be graded work, so a person will check it first. Edit or delete it any time." (the reason code picks the sentence). As built (`v2/chat-moderation-light`): chat's lines are one short sentence, "Only you can see this for now, until a person looks at it." (or "…: classmates reported it, so a person will look at it."), and a message waiting on a check (or a retry) shows nothing.

**Keep the human queue small.** The admin stats page shows the share of items held per surface per week. The target is under 5%; above 10% for a week, tune the thresholds or the prompt (a STATUS.md decision each time).

### 9.3 Reports

`reports/create {surface, ref, reason, note | null}` (`auth: "user"`), one per user per item. Reasons: `personal-info`, `names-a-student`, `hate`, `threat`, `sexual`, `misconduct-claim`, `graded-work`, `off-topic`, `other`. As built (`v2/chat-moderation-light`): those are Reviews'; chat takes abuse only, `hate`, `threat`, `sexual`, `spam`, `personal-info` and `other` with a note. An item is **hidden** until a person decides when 3 different people report it, or 1 reports `threat`, `personal-info` or `names-a-student`. Every report puts the item in the queue. All reporters weigh 1; there are no trust tiers.

### 9.4 D1 (migration `0004_moderation.sql`)

User ids here are plain `TEXT` without foreign keys, so this migration and `0003_identity.sql` can merge in either order.

```sql
-- Every automated and human decision, text-free. Kept a year.
CREATE TABLE moderation_decisions (
  id           TEXT PRIMARY KEY,
  surface      TEXT NOT NULL CHECK (surface IN ('review', 'chat')),
  ref          TEXT NOT NULL,                -- review id, or '<term>:<course>:<messageId>'
  stage        TEXT NOT NULL CHECK (stage IN ('rules', 'model', 'human', 'reports')),
  verdict      TEXT NOT NULL CHECK (verdict IN ('allow', 'hold', 'reject', 'remove', 'restore', 'hide')),
  labels       TEXT NOT NULL DEFAULT '[]',
  guard        TEXT,                         -- JSON: Llama Guard's answer
  policy       TEXT,                         -- JSON: the instruct model's verdict, confidence, labels
  models       TEXT,                         -- JSON: model ids used
  latency_ms   INTEGER,
  decided_by   TEXT NOT NULL CHECK (decided_by IN ('system', 'admin')),
  reason       TEXT,
  created_at   TEXT NOT NULL
);
CREATE INDEX moderation_decisions_by_ref ON moderation_decisions (surface, ref, created_at);
CREATE INDEX moderation_decisions_recent ON moderation_decisions (created_at);

-- The human queue. The snapshot is what the admin sees; blanked 30 days after close.
CREATE TABLE moderation_queue (
  id          TEXT PRIMARY KEY,
  surface     TEXT NOT NULL CHECK (surface IN ('review', 'chat')),
  ref         TEXT NOT NULL,
  snapshot    TEXT,                          -- JSON: text, course, activeAssignments, scores, retries; reviews: no author, ever
  labels      TEXT NOT NULL DEFAULT '[]',
  urgent      INTEGER NOT NULL DEFAULT 0,
  status      TEXT NOT NULL CHECK (status IN ('retry', 'open', 'closed')),  -- retry: waiting for the cron (§9.2)
  created_at  TEXT NOT NULL,
  closed_at   TEXT
);
CREATE UNIQUE INDEX moderation_queue_open ON moderation_queue (surface, ref) WHERE status IN ('retry', 'open');
CREATE INDEX moderation_queue_by_age ON moderation_queue (status, urgent DESC, created_at);

CREATE TABLE reports (
  surface      TEXT NOT NULL CHECK (surface IN ('review', 'chat')),
  ref          TEXT NOT NULL,
  reporter_id  TEXT NOT NULL,
  reason       TEXT NOT NULL,
  note         TEXT,                         -- ≤ 300 characters
  created_at   TEXT NOT NULL,
  PRIMARY KEY (surface, ref, reporter_id)
);
```

- `labels` holds the reasons (code, source, action, span); `policy` the scores. The shipped file is `migrations/0004_moderation.sql`.
- **The every-5-minutes cron** blanks `snapshot` 30 days after an item closes.
- **Urgent items** email and push the admin at once (`admin-urgent`), besides the daily digest.
- **The daily digest** (the daily job) emails the admin when the queue isn't empty. Its subject names the oldest: "Terpsicle: 4 waiting, oldest 3 days".
- A credible threat: remove it, and pass the content (not the author, for reviews) to UMPD. `/reviews/policy` says we do that.

## 12. Security

**CSRF**
- Every `/api/*` call stays `POST` with `Content-Type: application/json` (a cross-site form can't send that without a preflight, which is never granted), `z.strictObject` inputs, no CORS headers.
- **Plus an origin check** (`isSameOrigin` in `src/server/auth/guard.ts`) on every route with `auth: "user" | "admin"` and on the WebSocket upgrade: `Origin` must equal the request's own origin, and `Sec-Fetch-Site`, when present, must be `same-origin`. Otherwise `403`.
- `auth: "optional"` routes (feedback, which anyone can send) get the same origin check, since they write, and the session when there is one, but never a 401.
- The session cookie is `SameSite=Lax`, so cross-site subresource requests never carry it.
- The OIDC flow is bound to the browser by `state` in the signed `__Host-oauth` cookie (which also stops login CSRF), plus PKCE and `nonce`.
- Sign-out and every change are `POST`; no GET changes state (email one-click links are `POST` per RFC 8058; a GET to them shows a button).

**Rate limits.** The route table (each area's `src/server/<area>/api-routes.ts`, composed by `src/server/api/router.ts`) gains `auth` and `perUserPerHour` next to `perIpPerHour`. Per-IP keys stay `HMAC(CF-Connecting-IP)`; per-user keys are `user:<id>:<route>`; both use `counters`. A route has either limit or both (`route()` refuses one with neither); per-IP is checked first, per-user once the session is, both before the body is read. A worker test (`src/server/api/limits.test.ts`) holds per-user limits to `auth` routes and per-IP limits to every route anyone can call. `auth/sign-out` stays `auth` "none" with its per-IP limit only (identity's choice: it must clear a stale cookie, so it can't require a session, and there's no person to count without one). **Local test servers** (owner, 2026-10-05): `me` and `auth/test-sign-in` carry `localUnlimited`, which skips their per-IP limit when the request's host is loopback (`localhost`, `127.0.0.1`, `[::1]`) and its client is loopback or absent (`vite dev` sets `CF-Connecting-IP` from the socket), so a full e2e run on one machine doesn't run out of sign-ins. A deployed Worker's host is never loopback and Cloudflare overwrites `CF-Connecting-IP`, so production and previews are limited exactly as the table says; `limits.test.ts` holds both sides.

- `wss://` is listed for Safari versions that don't match it with `'self'`; previews and localhost use their own origin. `https://terpsicle.com` is `pnpm dev`'s live data origin (the same as `'self'` in production).

- **Our inline head scripts are allowed by hash, built from their source.** `src/lib/inline-scripts.ts` lists them; the Vite plugin `scripts/inline-scripts.ts` evaluates that list in Node, minifies each script, and serves the text as `virtual:terpsicle/inline-scripts` (the app renders it, `<InlineScript name>` or `INLINE_SCRIPTS.<name>` in a route's `head()`) and the hashes as `virtual:terpsicle/inline-script-hashes` (the Worker's CSP). Both builds read the same literals, so the hash always matches; rendering the source string itself wouldn't (each build prints functions differently), and a scripts test refuses any other inline script in `src/`. **To add one:** write it as a self-contained function stringified with its arguments (like `src/lib/theme.ts`), add it to `INLINE_SCRIPT_SOURCES`, render it by name. Nothing is hand-maintained.
- **TanStack's own inline scripts** (the dehydrated router state and stream markers) carry per-request data, so they can't be hashed: the Worker makes a 128-bit nonce per page, hands it to the render in the `x-terpsicle-csp-nonce` request header (always overwritten), and `src/router.tsx` passes it to the router's `ssr.nonce`; TanStack puts it on its scripts and a `csp-nonce` meta the client reads back.
- **Zod runs without eval.** Zod compiles object parsers with `new Function` and probes for it on first use; an enforced CSP would make it fall back, a report-only one reports every compile. The `zodJitless` head script sets `globalThis.__zod_globalConfig.jitless` before any app code loads. Web workers run without a CSP (their scripts come from `/assets`, which the Worker never serves).
- The CSP ships first as `Content-Security-Policy-Report-Only` (`CSP_REPORT_ONLY` in `headers.ts`) for a week, then `v2/csp-enforce` flips it. `e2e/csp.spec.ts` runs search, adding a section, the Travel tab and a route's map with zero violations.
- **Reports** go to `POST /api/csp-report` (`report-uri`, and `report-to` via `Reporting-Endpoints`). It logs one report in ten, at most five violations per request, cut down to the directive, what was blocked (a CSP keyword, `self` or another origin), the page's path and the source file (our path, or another origin): no query strings, script samples, IPs or user agents. No counter or D1 write: a report-only policy can fire on every page view.
- **Every Worker response** also gets `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and, over HTTPS, `Strict-Transport-Security: max-age=31536000` (Cloudflare wasn't sending HSTS for terpsicle.com, checked 2026-09-26; `includeSubDomains` and `preload` are the owner's call). **Pages** also get `Permissions-Policy: camera=(), microphone=(), geolocation=()` and `Cross-Origin-Opener-Policy: same-origin` (sign-in is a full-page redirect, not a popup). Files under `/assets` are served before the Worker runs and get none of these.

**Rendering user content.** Review and message text is rendered as text, never `dangerouslySetInnerHTML`. Links in chat are detected client-side and rendered with `rel="noopener noreferrer ugc" target="_blank"`.

**Secrets and logs.** Session tokens, flow cookies, VAPID keys and emails never go into logs or analytics. Admin checks read only the bundled `config/admins.txt` (plus `tadmin` in test mode).
