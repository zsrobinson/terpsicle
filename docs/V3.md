# Terpsicle v3: technical plan for Plan and Todo

The plan every v3 agent builds from. It turns the owner's decisions of 2026-09-26 (evening) into names, tables, routes and an order of work for two new products: **Terpsicle Plan**, a four-year planner, and **Terpsicle Todo**, deadlines from ELMS. `docs/V2.md` is the model and the foundation: v3 builds on its identity, plan sync, push, PWA and route table, and doesn't change them except where this document says so.

**Precedence.** The owner's decisions win, then this document, then `docs/V2.md`, then the older docs. Once a table or schema lands in code, the code wins (`DATA.md`'s rule) and the PR updates this document too. Anything not decided here: pick the simplest option consistent with this file, `DESIGN.md` §5 and `SPEC.md` §3.13, and state the interpretation in the PR.

**When.** Build v3 after v2's core lands. The waves (§11) say which v2 PRs each v3 PR needs; nothing here is a reason to hold up a v2 PR.

**Out of scope for v3's first release** (each has a home in §9 or is simply cut):
- **Degree requirements.** Plan tracks credits, GenEd and prerequisites. It doesn't audit a major, and no major's quirks (CS areas, SOCY research courses) are modeled. Reading requirements from the catalog is a later phase (§9.1).
- A GPA panel, "what if" grades, own todos typed in Terpsicle, the "exam in a week" and "new on the feed" notifications, study-group cards in Chat, the review-ask email, PDF transcript upload, share links for a four-year plan.
- Earshot and Orgs stay dropped.

## 2. Terpsicle Plan

### 2.1 What the first release does

- Eight fall and spring semesters as columns, plus "Before UMD" (AP and transfer credit) and any summer or winter term that has a course. Courses are blocks: code, credits (or grade, once taken), title, GenEd chips. Add, move and remove, with undo.
- **Credits:** earned, in progress and planned, against 120.
- **GenEd progress** from Testudo's GenEd codes (§2.7).
- **Prerequisite problems as information** (§2.8). They never block anything.
- **Wildcards:** placeholder blocks like `CMSC4XX` and "Any DSHS course" (§2.9).
- **Transcript paste import** (§2.10).
- **Sample templates**, starting with Computer Science (§2.11).
- **"View schedule"** hands the next semester to the scheduler (§2.12).
- **Works signed out** in the browser, like the scheduler; signing in syncs it (§2.4).
- The side panel says, always and quietly: "Terpsicle doesn't check your major's requirements. Your degree audit does." with a link to u.achieve. No audit, no requirement names.

### 2.2 The course index (R2 family `courses/`)

The scheduler's catalog is per term and covers only the terms Testudo lists (about four). A four-year plan needs every course, including ones not offered this term, so the catalog job publishes a **course index** across every term it has seen.

| Key | Schema | Written by | Named |
|---|---|---|---|
| `courses/manifest.json` | `CourseIndexManifestSchema` `{schemaVersion, generatedAt, search: {hash}, departments: [{code, hash}]}` | catalog job (6 h) | fixed |
| `courses/search.<hash>.json` | `CourseSearchFileSchema`: per course `[code, title, creditsMin, creditsMax, genEdCodes]`, sorted by code | catalog job | hashed |
| `courses/dept/<DEPT>.<hash>.json` | `CourseIndexDeptSchema`: per course `{title, credits, genEds, prerequisite, corequisite, restriction, crossListings, prereqs, offered}` | catalog job | hashed |

- **Source:** the newest term's department chunk that lists the course (active terms first, then archived ones still in R2). `offered` is the list of term ids the course appeared in, newest first, so the UI can say "Last offered Fall 2025" and "Usually offered in fall".
- `genEds` is the catalog's shape (`DATA.md` §3.2: groups that all apply, options within a group, with `condition`).
- `prereqs` is `parsePrerequisite(prerequisite)` (§2.8), computed in ingest so every client gets the same answer.
- Sizes: the search file is about 5,000 rows (~120 KB gzipped). Department files load when a plan has a course from that department or a search result opens.
- `SCHEMA_VERSIONS` gains `courses`. Caching follows `dataCachePolicy` like `catalog/` (fixed manifest `no-cache`, hashed files immutable). Mock mode builds the index from `src/fixtures` with the same code.
- `src/state/course-index-store.ts` mirrors the catalog store's flow (`DATA.md` §5.1): cached manifest, diff, fetch changed files, one Dexie transaction, `mock:` prefixes.

### 2.3 The four-year doc (`src/core/schema/four-year.ts`)

Code names stay unambiguous: the scheduler already has "plans" (Plan A, Plan B). The four-year plan is **`FourYear`** in code (`src/core/four-year`, `src/features/four-year`, sync kind `four-year`), and **Plan** only in UI copy and the route.

```ts
export const FourYearTermSchema = z.union([TermIdSchema, z.literal("before")]); // "before" = AP and transfer

export const FourYearEntrySchema = z.discriminatedUnion("kind", [
  z.object({
    kind: z.literal("course"),
    id: LocalIdSchema,
    term: FourYearTermSchema,
    code: CourseCodeSchema,
    /** Only for variable-credit courses; otherwise the index's credits. */
    credits: z.number().min(0).max(20).nullable(),
    /** The option picked where Testudo says "or", per GenEd group index. */
    genEdChoices: z.record(z.string(), GenEdCodeSchema),
    source: z.enum(["typed", "transcript", "template"]),
    /** The transcript's own title and kind, shown under the catalog title. */
    transcript: z.object({ title: z.string().max(120), via: z.enum(["umd", "ap", "transfer"]) }).nullable(),
  }),
  z.object({
    kind: z.literal("wildcard"),
    id: LocalIdSchema,
    term: FourYearTermSchema,
    wildcard: WildcardSchema,           // from ~/core/wildcards (§2.9)
    credits: z.number().min(0).max(20), // default 3
    source: z.enum(["typed", "template"]),
  }),
  z.object({
    /** AP or transfer credit with no UMD equivalent ("CHEM 1XX, 4 credits"). */
    kind: z.literal("credit"),
    id: LocalIdSchema,
    term: z.literal("before"),
    title: z.string().min(1).max(120),
    credits: z.number().min(0).max(40),
    genEds: z.array(GenEdCodeSchema),
    source: z.literal("transcript"),
  }),
]);

export const FourYearDocSchema = z.object({
  id: LocalIdSchema,
  name: z.string().min(1).max(60),          // "My plan"; "(copy)" rules as plans
  firstTermId: TermIdSchema,                // the first fall shown
  /** Entries in column order: term, then position. */
  entries: z.array(FourYearEntrySchema).max(150),
  /** Private (§2.5). Keyed by entry id; only course entries have one. */
  grades: z.record(LocalIdSchema, GradeSchema),
  /** Where a template came from, for its credit line. */
  template: z.object({ id: z.string(), department: z.string(), year: z.string() }).nullable(),
  createdAt: IsoDateTimeSchema,
  updatedAt: IsoDateTimeSchema,
});
// GradeSchema (src/core/schema/transcript.ts): "A+" … "F", "XF", "P", "S", "I", "NG", "AUD"
// (W, NC and dropped lines aren't imported).
```

- **Several docs, one open.** People mostly keep one, but a copy ("what if I switch majors") is a natural thing to want, and ids cost nothing now. The name has a ▾ menu like a plan tab: Rename, Duplicate, Delete (Undo), New. The open one is `UiPrefs.activeFourYearId` (local, not synced).
- **Status is derived, never stored:** `termStatus(term, today, calendars)` in core says `done`, `in-progress` or `planned` from the academic calendar (`calendar/<term>.json`: in progress from `classesStart` until 14 days after `classesEnd`, for finals and grades; by the season's months when the calendar isn't published). "Before" is always done.
- **Local first:** Dexie gains a `fourYear` table (key `id`) in the Dexie version after v2's (`LOCAL_DB_VERSION` + 1, with an `upgrade()`). Rows are validated on read like plans; an invalid row is skipped and logged, never fatal.
- **Undo** is the scheduler's reducer pattern (`src/core/plans/history.ts`): `fourYearReducer` in `src/core/four-year/reducer.ts` with actions `add`, `move`, `remove`, `resolve-wildcard`, `set-choice`, `set-credits`, `apply-template`, `import`, `rename`, `remove-grades`; ⌘Z and the toast's Undo.

### 2.4 Sync: a new doc kind (migration `0010_four_year_sync.sql`)

A four-year doc is a third sync doc kind, next to `plan` and `settings` (V2 §5), with the same rules: saved whole with its base rev (compare-and-swap), never merged field by field.

- **Why a new kind and not part of the settings doc:** it's a person's biggest document, edited in bursts; inside the settings doc every GenEd choice would conflict with a block edit on another device. As its own doc, a conflict keeps both copies, the rule people already know.
- **The migration** rebuilds `sync_docs`, because SQLite can't alter a `CHECK`:
  - `kind IN ('plan', 'settings', 'four-year')`;
  - `CHECK (kind IN ('plan', 'four-year') OR deleted = 0)` (four-year docs have tombstones too);
  - `term_id` stays NULL for four-year docs.

  It runs as create `sync_docs_new` → copy → drop → rename → recreate `sync_docs_since` and `sync_docs_tombstones`, with `PRAGMA defer_foreign_keys = on`. Nothing references `sync_docs`, so the rebuild is local to it. A worker test applies every migration in order and round-trips existing rows.
- **Schemas:** `SyncDocKindSchema` gains `"four-year"`; `SyncDocSchema`, `SyncPushDocSchema` gain the branch (body `FourYearDocSchema`, body id = doc id). Limits: the same 64 KiB body; at most `SYNC_MAX_FOUR_YEAR_DOCS` = 20 live four-year docs per user (the `too-many-plans` result covers it; the UI says "You have 20 four-year plans. Delete one to make another.").
- **Older tabs must not break.** A tab from before this deploy parses pull results with a union that doesn't know `four-year`. So the first PR that touches sync (§11, `v3/four-year-sync-api`) makes the client parse pulled docs one by one and **skip a doc of an unknown kind** (logged, not fatal) instead of failing the page. And because a skipping client still advances its cursor, the Dexie upgrade that adds `fourYear` **resets the sync cursor to 0** once, so an upgraded device pulls everything and sees the four-year docs it skipped. A push that carries a four-year doc is answered `unavailable` until `PLAN_ENABLED` is on, which is a later deploy.
- **Server:** nothing reads a four-year body beyond validating it. `chat_members` is derived from plan docs only. The admin panel never shows sync docs.
- **Conflicts and first sign-in** reuse `src/core/sync` unchanged in spirit: a conflicting four-year doc is kept both ways ("<name> (copy)"); first sign-in uploads every local four-year doc the account lacks, and an untouched empty "My plan" isn't uploaded to an account that already has one. The toast counts plans and four-year plans together: "Your 3 plans and your four-year plan are on your account now. Nothing was dropped."
- **Sign-out** "and remove plans from this device" also clears `fourYear`.

### 2.5 Grades are private

Grades come in with the transcript (the import's "Keep grades" checkbox, on by default) and show on done blocks. They exist for the person looking at their own plan, and later for a GPA panel.

- **Where they live:** only in the four-year doc's `grades` map, in the browser and, when signed in, in that doc on our server so they're on your other devices. One map, so "Remove grades" (in the doc's ▾ menu, with Undo) is one action and easy to verify.
- **Never anywhere else:** not in share links (four-year plans have none), exports, analytics events or properties, logs, error messages, push payloads, email, the admin panel, Chat, Reviews or any server computation. The server stores the body and never parses `grades`.
- **Never shown to anyone else.** No feature shows one person's plan to another.
- **Not imported:** W, NC, dropped and in-progress lines (they have no grade); the import's check step says which lines it left out and why.
- **UI:** grades carry `data-private`, and session recordings are off on `/plan` (§6).
- **Honest copy** on the import: "Grades stay in your plan. If you're signed in, they sync to your other devices through Terpsicle's server. Nobody else can see them." and on `/privacy` (§5.3). Sync is plain server-side storage, not end-to-end encrypted (V2 §5.1), and the copy doesn't pretend otherwise.

### 2.6 Credits (`src/core/four-year/credits.ts`)

- A course counts its index credits (or the entry's `credits` for a variable-credit course); a wildcard its own `credits`; a `credit` entry its credits.
- **Earned** = done terms, excluding F; **in progress** = the current term; **planned** = later terms. "Before UMD" counts as earned.
- A course taken twice counts once, the later attempt, and raises a `repeated-course` problem unless the catalog marks it repeatable ("Repeatable to 6 credits" in `otherNotes`).
- The header reads "99 of 120 credits", with the tooltip "Most UMD degrees need 120 credits. Yours may need more; your degree audit has the number."
- Per column: courses and credits ("5 courses · 15 cr").

### 2.7 GenEd progress (`src/core/four-year/gen-ed.ts`)

- **Categories and counts** are a small hand-kept constant, `GEN_ED_REQUIREMENTS`, with its source (UMD's GenEd checklist) in a comment. They change rarely. First release:

  | Code | Label | Needed |
  |---|---|---|
  | FSAW, FSPW, FSOC, FSMA, FSAR | Fundamental Studies | 1 each |
  | DSNL, DSNS | Natural Sciences | 2, at least one DSNL (lab) |
  | DSHS | History and Social Sciences | 2 |
  | DSHU | Humanities | 2 |
  | DSSP | Scholarship in Practice | 2 |
  | SCIS | I-Series | 2 |
  | DVUP, DVCC | Diversity | 2, at least one DVUP |

- **Which course counts** comes from the course's `genEds` (DATA.md §3.2): every group applies; within a group the course counts for one option. Where a group has options, the entry's `genEdChoices` wins; otherwise `allocateGenEds` picks, pure and deterministic: done courses first, then in term order, each open option going to the category that's furthest from done. A choice the person made is never overridden.
- **Conditions:** "DSNL (if taken with GEOL110)" counts as DSNL only when GEOL110 is in the same or an earlier semester; otherwise the chip shows the condition and the course counts as DSNS if that's its other option.
- I-Series and Diversity count alongside a Distributive Studies code, as Testudo's groups already say.
- **The panel** (`?tab=gened`): one row per category with done, planned and still needed ("2 done · 1 planned · of 2"), and for a category still short, "Find a course" → `?tab=search` with the GenEd filter. The footer: "From Testudo's GenEd codes. Your degree audit is the official check."

### 2.8 Prerequisite problems (`src/core/four-year/prereqs.ts`, `problems.ts`)

Prerequisites are information. Nothing blocks a move, and nothing turns red (DESIGN §5).

- **Parsing** (`parsePrerequisite(text)` in `src/core/catalog/prereqs.ts`, run in ingest): Testudo's sentence is free text. The parser pulls course codes (`[A-Z]{4}\d{3}[A-Z]?`, and "CMSC 131" with a space) and splits clauses on `;` and ` and ` into groups that all apply, with ` or ` inside a group: `{groups: CourseCode[][], complete: boolean}`. `complete` is false whenever the sentence has anything else: "permission of", "or equivalent", scores, "must have completed", program names. **Golden tests** run it over every prerequisite sentence in the saved terms' fixtures and snapshot the results, so a change shows up in review.
- **The check:** each group needs one of its codes (or a cross-listed equivalent) in an earlier semester, "Before UMD" and the current term included. A course's own term never counts. Wildcards and `credit` entries satisfy nothing.
- **Problem kinds** (`FourYearProblem`, same `MessagePart` shape as the scheduler's `Problem`, DATA.md §9):

  | Kind | Severity | When | Example |
  |---|---|---|---|
  | `prereq-order` | info | a group isn't met by an earlier semester | "CMSC351 is before CMSC250" |
  | `light-semester` | info | a planned fall or spring has 1–11 credits | "Fall 2028 has 6 credits. Full time is 12." |
  | `repeated-course` | info | the same course twice, not repeatable | "CMSC216 is in Fall 2026 and Spring 2027" |
  | `unknown-course` | warning | a code the index doesn't know | "HIST999 isn't in Testudo" |
  | `not-offered-lately` | info | not in any of the last four fall/spring terms | "ARTT489 was last offered Spring 2024" |

- **Every prerequisite problem shows Testudo's sentence** ("Testudo says: Minimum grade of C- in CMSC250 and CMSC216."), because the parser can't read everything and grade minimums aren't checked.
- **Fixes** follow the scheduler's rule: offered only when they create no new problem. `prereq-order` offers "Move CMSC351 to Spring 2027" (the first semester where every group is met); `repeated-course` offers "Remove the later one". Undo applies.
- A block with a problem gets the thin warning inset the prototype shows, never a red outline; the problem and its fix live in the Problems tab.

### 2.9 Wildcards (the shared matcher from `v2/wildcards`)

The scheduler's Generate tab and Plan share one matcher in core, being built separately in **`v2/wildcards`** (`src/core/wildcards`). Plan uses it and adds nothing to it. The contract Plan builds against (if `v2/wildcards` lands different names, its names win and the implementing PR updates this section):

```ts
WildcardSchema = z.discriminatedUnion("kind", [
  z.object({ kind: z.literal("pattern"), pattern: z.string() }),  // "CMSC4XX", "SOCY4XX", "ARTTXXX"
  z.object({ kind: z.literal("gen-ed"), code: GenEdCodeSchema }), // any DSHS course
]);
parseWildcard(text: string): Wildcard | null;
matchesWildcard(course: { code: CourseCode; genEds: GenEdGroup[] }, w: Wildcard): boolean;
wildcardLabel(w: Wildcard): string;   // "CMSC4XX", "Any DSHS course"
```

In Plan:
- **Adding:** typing `CMSC4XX` or "any DSHS" in Plan's search offers "Add a placeholder: CMSC4XX" as the first result. A template can include them.
- **A placeholder block** is dashed, shows its label and credits (default 3, editable 1–6), and counts toward credits. A GenEd wildcard counts as *planned* for its category; a pattern wildcard counts toward no category. Placeholders satisfy no prerequisite and have no prerequisites.
- **Resolving:** "Pick a course" opens `?tab=search&wildcard=<id>` with the matcher as a filter; choosing one replaces the block in place (Undo).
- **Handoff:** placeholders can't become scheduler bookmarks; §2.12 says what happens.

### 2.10 Transcript import

**A pure core parser with golden tests** (`src/core/four-year/transcript/parse.ts`); the UI is the Import tab.

```ts
parseTranscript(text: string): TranscriptParse;   // schemas in src/core/schema/transcript.ts
// TranscriptParse = {
//   lines: TranscriptLine[],     // what we read, in order
//   skipped: { raw: string, reason: "withdrawn" | "dropped" | "no-credit" | "unreadable",
//              line: TranscriptLine | null }[],   // what it would import as (null: unreadable)
//   recognized: boolean,         // false: this doesn't look like a UMD unofficial transcript
// }
// TranscriptLine = { term: TermId | "before", code: CourseCode | null, title: string,
//   grade: Grade | null, credits: number, earned: number | null, qualityPoints: number | null,
//   genEds: GenEdGroup[], via: "umd" | "ap" | "transfer", equivalentOf: CourseCode | null,
//   equivalentPattern: string | null, sectionCode: SectionCode | null, inProgress: boolean }
```

- **As built** (`v3/transcript-parser`): `code` is the UMD course a line counts as, so for AP and transfer lines it equals `equivalentOf`, and it's null when the credit has no single UMD course. A generic equivalent (`CHEM 1XX`) is kept as `equivalentPattern` for the check step's transfer mapping. `skipped[].line` is what the check step ticks back in. Columns are told apart by gaps of two or more spaces (or a tab), which is how "VITAMIN D" stays a title and `INTRO   D   3.00` reads as a drop; indentation isn't needed. The golden pastes are synthetic until owner action 1 (`src/core/four-year/transcript/__fixtures__/README.md` says how a redacted real paste replaces them).

- **The format**, from v1's `lib/transcript-parser.ts` (terpsicle-bitcamp, 2025): everything before the first line containing `@` is header and is ignored; transfer and AP lines come first, with a grade of `P`, `NC` or a letter, credits like `3.00`, the UMD equivalent's code and GenEd codes after it; then term lines (`Fall 2025`); course lines are indented at least four spaces: code, title, grade, credits attempted, earned, quality points, GenEd codes; in-progress terms carry a four-digit section code as the second token and no grade; a `D` marks a dropped course; lines starting with `Meth` or `=` are page furniture. GenEd lists split on `,` into groups and on ` or ` into options, the same shape as the catalog's.
- **The first job is a fresh paste** (owner action, §10): the layout may have moved since 2025. v1's parser is a guide, not a spec.
- **Golden tests** on real pastes in `src/core/four-year/transcript/__fixtures__/`, redacted before they're committed: name, UID, birth date, address and email replaced with fixed fakes, and a test asserts the fixtures contain none of the original values' shapes (a 9-digit UID, an email other than the fake). At least: a plain four-semester paste, one with AP and transfer credit, one with a W, a drop and an in-progress term. `parseTranscript` throws on nothing: bad input gives `recognized: false`.
- **Header data never leaves the parser.** Names, UIDs and addresses aren't in `TranscriptParse`. The paste lives in component state only: never stored, never sent, never logged, never in the URL, never in analytics or error reports.
- **Matching:** each line's code is looked up in the course index. The catalog title shows with the transcript title under it. A transfer line with no equivalent becomes a `credit` entry. A code the index doesn't know stays a course entry with an `unknown-course` problem.

**The Import tab** (`?tab=import`): three steps, Paste → Check → Import.
1. **Paste.** "In Testudo, open Unofficial Transcript, select everything on the page (⌘A), copy, and paste it here. Nothing leaves your browser until you import." Parsing runs as you paste.
2. **Check.** What we read, by semester, live next to the paste on desktop and as a list on the phone. Three fix-ups only: choose the GenEd where Testudo says "or" (the Import button waits until each is chosen), tick a skipped line back in, and map a transfer course we couldn't match. "Keep grades" checkbox, on.
3. **Import.** One `import` action: it replaces the doc's done and in-progress terms with what was read (typed entries in those terms are kept only if the transcript doesn't have them) and leaves planned terms alone. Undo in the toast. If the plan is empty, `firstTermId` becomes the transcript's first fall or spring. The toast: "Imported 16 courses from 4 semesters."

## 3. Terpsicle Todo

### 3.1 What the first release does

- **Connect ELMS** by pasting the ELMS calendar feed link (an `.ics` URL). One paste, no password, no approval from UMD.
- **The list by day** (Today, Tomorrow, This week, Next week, Later), with checkboxes, on the phone and desktop; **by course** as a second view; on desktop, **the week** with a Due lane above the scheduler's calendar grid, classes from the current term's linked plan.
- **Exams** (items whose titles read like one) are marked, and dashed on the week.
- **One notification**, "Due tomorrow" (§4).
- **Gradescope**, honestly: tagged where ELMS already carries it, plus a file-drop fallback (§3.7).
- **Signed in only.** Not in the first release: own todos, "exam in a week", "new on the feed", marking done in ELMS.

**Why the calendar feed.** The prototype compared three ways in. The feed needs no approval and covers dated assignments, quizzes and calendar events for every course. A personal access token would put the student's whole ELMS in our database and may be disabled for students; LTI or a developer key needs DIT's approval, which a student project won't get. The feed's known limits (reported by campus IT pages): about 1,000 items, a year ahead and 30 days back, no undated work, no ELMS to-do items, no grades. Copy says what does and doesn't come through: "Assignments, quizzes and exams with a due date, and events your professors put on the ELMS calendar. Undated work and grades don't come through."

### 3.2 Connecting (`todo/connect`)

**The link is a secret:** anyone with it can read that student's due dates. It's handled like a password from the moment it's pasted.

1. **Shape check, in the browser and again on the server** (`parseFeedLink` in `src/core/todo/link.ts`, pure): after trimming, it must be exactly `https://<host>/feeds/calendars/user_<token>.ics` with `<host>` one of `elms.umd.edu` and `umd.instructure.com`, and `<token>` 20–80 characters of `[A-Za-z0-9]`. No other host, port, path, query, fragment or credentials. The answer to a bad link never echoes it: "That isn't an ELMS calendar link. In ELMS, open Calendar, click Calendar Feed, and copy the link." (`webcal://` is accepted and rewritten to `https://`, since some browsers copy that.)
2. **One fetch before storing** (§3.5's fetcher): it must answer 200 with a body that parses as a calendar. Failures answer `unreachable` ("ELMS didn't answer. Try again in a minute.") or `not-a-calendar`. Nothing is stored on failure.
3. **Store it encrypted** (§3.3), upsert the `todo_feeds` row, write the items, and answer `{status: "connected", items, feed}`. Reconnecting replaces the link and keeps done marks for items that come back with the same UID.

**The connect page** (`/todo/connect`): three numbered steps ("Open elms.umd.edu and go to Calendar." / "Click Calendar Feed at the bottom right and copy the link." / "Paste it here.") and the note: "This link is a secret: anyone with it can read your due dates. We keep it encrypted and fetch it from our server, so reminders work when the app's closed. Disconnect any time." The input is `type="url"`, `autocomplete="off"`, `spellcheck="false"`, `data-private`, and `ph-no-capture`; the value is sent only in the `todo/connect` POST body and cleared from state after the answer.

**Disconnect** (`todo/disconnect`): no dialog. The UI shows the disconnected state at once with Undo in the toast and calls the route after the toast's 8 seconds (the pattern `reviews/delete` uses). The route deletes the feed row, its items and done marks in one batch.

### 3.3 Encrypting the link

- **AES-256-GCM** with WebCrypto, key from the Worker secret **`TODO_FEED_KEY`** (32 random bytes, base64url), imported once per isolate as a non-extractable key.
- **Stored as one string** in `todo_feeds.url_enc`: `v1.<keyId>.<iv>.<ciphertext>` (base64url; a fresh 12-byte IV each time). `keyId` is the var `TODO_FEED_KEY_ID` (`"k1"` at first).
- **Bound to its row:** the additional authenticated data is `todo-feed:<userId>:<source>`, so a ciphertext copied to another user's row won't decrypt.
- **Rotation:** set the new key as `TODO_FEED_KEY` with a new `TODO_FEED_KEY_ID`, and the old one as `TODO_FEED_KEY_PREVIOUS` (with `TODO_FEED_KEY_PREVIOUS_ID`). Reads try the key whose id the row names; the fetch cron re-encrypts rows under the current key as it touches them; once none name the old id, remove `TODO_FEED_KEY_PREVIOUS`.
- `src/server/todo/crypto.ts` has the only code that decrypts, and it hands the URL only to the fetcher. No other function, route or log sees it.
- Missing key (previews, `pnpm dev:mock`): `todo/*` answers `unavailable` except in test mode, where `pnpm dev:mock` and e2e use a fixed test key and a fixture feed server (§11, `v3/todo-e2e`).

### 3.4 D1 (migration `0011_todo.sql`)

```sql
-- A connected source per user. Only 'elms' is fetched; the key leaves room for
-- another source without a rebuild.
CREATE TABLE todo_feeds (
  user_id          TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  source           TEXT NOT NULL CHECK (source IN ('elms')),
  url_enc          TEXT NOT NULL,             -- v1.<keyId>.<iv>.<ciphertext>; never logged, never returned
  status           TEXT NOT NULL CHECK (status IN ('active', 'paused', 'broken')),
  created_at       TEXT NOT NULL,
  next_fetch_at    TEXT NOT NULL,
  last_fetch_at    TEXT,
  last_success_at  TEXT,
  failure_count    INTEGER NOT NULL DEFAULT 0, -- consecutive
  last_error       TEXT,                       -- a code: 'timeout', 'http-404', 'not-a-calendar', …
  etag             TEXT,
  last_modified    TEXT,
  content_hash     TEXT,                       -- 16 hex of SHA-256 of the body: unchanged feeds write nothing
  item_count       INTEGER NOT NULL DEFAULT 0,
  last_opened_at   TEXT NOT NULL,              -- the person last loaded /todo (for the cadence)
  PRIMARY KEY (user_id, source)
);
CREATE INDEX todo_feeds_due ON todo_feeds (status, next_fetch_at);

-- Items from the feed or a dropped file. Rewritten by each fetch.
CREATE TABLE todo_items (
  user_id       TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  uid           TEXT NOT NULL,                -- the ICS UID (≤ 200 chars)
  source        TEXT NOT NULL CHECK (source IN ('elms', 'file')),
  title         TEXT NOT NULL,                -- SUMMARY without the course bracket, ≤ 300 chars
  course_label  TEXT,                         -- the bracket's text: "CMSC216-0103: Introduction to Computer Systems"
  course_code   TEXT,                         -- matched from course_label (§3.6), or null
  section_code  TEXT,
  kind          TEXT NOT NULL CHECK (kind IN ('assignment', 'event')),
  exam          INTEGER NOT NULL DEFAULT 0,   -- the title reads like an exam or quiz
  gradescope    INTEGER NOT NULL DEFAULT 0,   -- §3.7
  due_at        TEXT,                         -- instant; null for an all-day item
  due_date      TEXT NOT NULL,                -- America/New_York date of due_at, or the all-day date
  link          TEXT,                         -- an ELMS URL from the item, same hosts as §3.2, or null
  first_seen_at TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  PRIMARY KEY (user_id, uid)
);
CREATE INDEX todo_items_by_date ON todo_items (user_id, due_date);
CREATE INDEX todo_items_due_day ON todo_items (due_date, user_id);

-- Done marks, kept apart from items so a refetch never clears them.
CREATE TABLE todo_done (
  user_id  TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  uid      TEXT NOT NULL,
  done_at  TEXT NOT NULL,
  PRIMARY KEY (user_id, uid)
);
```

- Rows are validated on read with `TodoFeedRowSchema`, `TodoItemRowSchema` (`src/server/todo/store.ts`), like `alerts/store.ts`. `TodoFeedRowSchema` never includes `url_enc` in anything it returns to a handler; only `crypto.ts` reads that column.
- **Window:** only items with `due_date` from 30 days ago to 365 days ahead are kept; at most 1,500 per user. Descriptions are never stored (they're long, may be HTML, and we don't show them).
- **Pruning** (the daily job): items with `due_date` more than 30 days ago, and `todo_done` rows whose item has been gone for 30 days.
- **Account deletion** cascades every table. Disconnect deletes at once (§3.2).

### 3.5 Fetching: cadence and backoff (`src/jobs/todo-feeds.ts`, `src/server/todo/fetch.ts`)

**A cron every 20 minutes** at `"3,23,43 * * * *"` (off the seats job's minutes). Each run takes the feeds with `status = 'active'` and `next_fetch_at <= now`, oldest first, up to `TODO_FETCH_BATCH` (400), 8 at a time.

**The fetcher** (the only code that fetches a feed):
- `GET` the decrypted URL with `redirect: "manual"`; follow at most 2 redirects, each re-checked with `parseFeedLink`'s host rule; anything else is `bad-redirect`.
- 10 s timeout; a body over 5 MB is cut off and counts as `too-large`.
- Sends `If-None-Match` / `If-Modified-Since` when we have them; a 304 or an unchanged `content_hash` updates only the feed row's timestamps.
- **Errors become codes**, never messages: `fetch()` errors and `Response` objects can carry the URL, so the fetcher catches everything and returns `{ok: false, code}` with a code from a fixed list (`timeout`, `network`, `http-<status>`, `too-large`, `not-a-calendar`, `bad-redirect`). Nothing from the error object is kept.

**Cadence:**

| Feed | Next fetch |
|---|---|
| Opened `/todo` in the last 14 days, or "Due tomorrow" on | 20 min |
| Otherwise | 6 h |
| Not opened in 120 days and "Due tomorrow" off | `paused`: not fetched. Opening `/todo` resumes it and fetches at once. |

**Backoff:** after a failure, `next_fetch_at = now + min(20 min × 2^(failures − 1), 12 h)`, with ±10% jitter so failures don't bunch. `http-401`, `http-403`, `http-404` and `http-410` mean ELMS stopped sharing that link (a reset feed or a removed account): three in a row, at least an hour apart, set `status = 'broken'` and stop fetching. `/todo` then says, in place and without a banner: "ELMS stopped sharing your calendar. Paste a new link." Other failures never break a feed; the list shows "ELMS feed checked 3 hours ago" so stale data is visible.

**On demand:** `todo/refresh` (the list's refresh control, and on opening `/todo` when the last success is over 10 minutes old) fetches that one feed now, at most once per 5 minutes per user.

**Writing:** parse (§3.6), then one D1 batch per feed: upsert items that changed, delete items no longer in the feed (their done marks stay until pruning), update the feed row. Unchanged feeds write one row.

**Scale:** at 400 feeds per run and three runs an hour, about 8,000 active feeds keep a 20-minute cadence; beyond that the cadence stretches and nothing is dropped. The admin health header (V2 §10) shows active, paused and broken feeds and the last run. Moving fetching to a Queue is a later PR if it's ever needed.

### 3.6 Parsing the feed and matching courses (`src/core/todo/`, pure)

- **`parseIcs(text)`**: a small RFC 5545 subset, no library: unfold lines, read `VEVENT`s' `UID`, `SUMMARY`, `DTSTART` (a `DATE`, a UTC `DATE-TIME`, or one with `TZID`), `DTEND`, `URL` and `DESCRIPTION` (read only for §3.7's flag, then dropped); unescape text. Anything unreadable is skipped and counted, never fatal. `recognized` is false when there's no `BEGIN:VCALENDAR`.
- **Kind:** `assignment` when the UID names one (`event-assignment-…`), else `event`. The due time is `DTSTART` (Canvas puts an assignment's due time there).
- **Exam:** `looksLikeExam(title)`: `\b(exam|midterm|final|quiz|test)\b`, case-insensitive, with a short exclusion list ("final project", "final paper", "test case"). It's a display hint only.
- **Course matching:** Canvas titles end with the course in brackets: `Project 2 [CMSC216-0103: Introduction to Computer Systems]`. `splitFeedTitle(summary)` takes the last `[...]` as `course_label` and the rest as `title`. `matchFeedCourse(label)` finds `[A-Z]{4}\d{3}[A-Z]?`, optionally followed by `-` and a four-character section; with several codes (merged sections, cross-listings like `CMSC216/ENEE…`), all are returned in order. The server stores the first; the client re-matches against the person's plans with `pickFeedCourse(codes, planCourses)` (the first code in the linked plan for the item's term, else the first code) to color the item with that course's scheduler color. An item with no code keeps its ELMS course name and a neutral color.
- **Which term:** `termForDate(date, calendars)` picks the term whose calendar span (classes through 14 days after) contains the date.
- **Golden tests** on a real feed (owner action, §10), recorded with `scripts/record-ics-fixture.ts`, which fetches a feed the owner passes on stdin (never as an argument, so it stays out of shell history), keeps structure, UIDs, dates and course labels, replaces assignment titles with fixed fakes where the owner asks, and writes `src/core/todo/__fixtures__/elms-<date>.ics`. The script prints nothing about the URL.

- **As built** (`v3/ics-parser`): `parseIcs(text, source = "elms")` → `IcsParse` `{recognized, items: FeedItem[], skipped}` (`src/core/schema/ics-feed.ts`). A `FeedItem` carries `uid`, `source`, `title`, `courseLabel`, `courseCodes` (all of them; the server stores the first), `sectionCode`, `kind` with `kindFrom` (`uid` when Canvas's UID says; `title` when a dropped file makes us guess from words like "Homework" or "Lab"), `looksLikeExam` (always a keyword guess, named as one; it's the D1 `exam` column), `gradescope`, `dueAt`, `dueDate`, `endAt` and `link` (ELMS hosts only). Events sharing a UID become one item (higher `SEQUENCE`, else the later one); `STATUS:CANCELLED` events are left out; a recurring event is read as its first occurrence. A floating time (no `TZID`) is read in New York; a `TZID` Intl can't place (or Outlook's Windows names, which are mapped) makes the event unreadable. Times in the hour daylight time skips or repeats follow RFC 5545 §3.3.5. Until owner action 2, the golden feeds are synthetic (`src/core/todo/__fixtures__/README.md`); `scripts/record-ics-fixture.ts` redacts a real one (the calendar's name, descriptions, locations, personal-calendar titles and user ids; `--fake-titles` for every title).

### 3.7 Gradescope

Gradescope has **no student API, feed or export**, and its terms forbid scraping. So Terpsicle **never stores a Gradescope or ELMS password, never automates a login, and never fetches gradescope.com**.

- **The main path is ELMS.** UMD connects Gradescope to ELMS with LTI 1.3, so Gradescope assignments linked in an ELMS course already appear in the ELMS calendar feed. An item whose `URL` or `DESCRIPTION` mentions `gradescope.com` gets `gradescope = 1` and a "Gradescope" tag in the list.
- **Extensions don't sync.** An individual extension set only in Gradescope doesn't reach ELMS. Todo says so, once, under a Gradescope item's detail and on the connect page: "Extensions you get in Gradescope don't show up in ELMS. Check Gradescope for your own due date."
- **Fallback: drop a file.** On `/todo/connect`, "Add a calendar file" takes an `.ics` the student exported themselves (for example with a browser extension on their own machine). It's parsed **in the browser** with the same `parseIcs`; only the structured items (UID, title, course label, dates, kind, exam) go to `todo/import-file`, which stores them with `source = 'file'`, skipping any UID the ELMS feed already has. A new file replaces the previous file's items. At most 2 MB and 1,000 items. Items are marked "From a file", and there's no server fetch for them, so they don't update: the page says "Files don't update. Drop a new one when your deadlines change."
- The file's raw text never leaves the browser.

### 3.8 API (`src/server/todo/`, all `auth: "user"`)

| Endpoint | Input → result |
|---|---|
| `todo/connect` | `{url}` → `{status: "connected", feed, items}` \| `{status: "invalid-link"}` \| `{status: "unreachable"}` \| `{status: "not-a-calendar"}` |
| `todo/disconnect` | `{}` → `{status: "disconnected"}` |
| `todo/list` | `{from: IsoDate, to: IsoDate}` (≤ 120 days) → `{feed: TodoFeedState \| null, items: TodoItem[], done: string[]}`; records `last_opened_at` (at most one write an hour) |
| `todo/done` | `{uid, done: boolean}` → `{status: "ok"}` |
| `todo/refresh` | `{}` → `{status: "fetched" \| "too-soon" \| "failed", feed}` |
| `todo/import-file` | `{items: TodoFileItem[]}` (≤ 1,000) → `{status: "imported", added, skipped}` |

- `TodoFeedState` = `{source, status, lastSuccessAt, lastFetchAt, lastError, itemCount}`. There's no field that could hold the URL, and a worker test asserts no answer from any `todo/*` route contains the fixture feed's token.
- `TODO_ENABLED` (var): `off` → every route `unavailable` and Todo leaves the product menu; `on`. Previews: `on` with test mode.
- Rate limits: `todo/connect` 10 per user per hour (and 30 per IP); `todo/list` 600; `todo/done` 1,200; `todo/refresh` 30 (plus the 5-minute rule); `todo/import-file` 20; `todo/disconnect` 30.
- The client keeps done marks optimistic and keeps the last list in memory only. Nothing from Todo is written to IndexedDB in the first release: the data is the server's, and a shared computer shouldn't keep a student's deadlines.

## 4. Notifications: "Due tomorrow"

"Not too many notifications": V2 has four types and said don't add more. **`todo-due` is the owner's one approved exception**, with these limits:

| Type | Push | Email | Default | Sent when |
|---|---|---|---|---|
| `todo-due` | ✓ | — | **off until ELMS is connected**; connecting turns push on | At 6pm New York time, if at least one item due tomorrow isn't done. **At most one a day.** |

- **Settings:** `NotificationSettingsSchema` gains `todoDue: z.object({ push: z.boolean() }).default({ push: false })`, an additive field on the JSON column (no version bump; a stored row without it reads as off). `todo/connect` sets it to `true` the first time a feed connects; the person can turn it off. `/settings/notifications` shows the row only while a feed is connected; otherwise it says "Connect ELMS in Todo to get this."
- **Push only.** No email channel in the first release: one reminder a day is the whole promise, and email would double it for people with both.
- **Sending** rides on the Todo cron (§3.5): the first run at or after 18:00 America/New_York (computed in core from the run's time, so daylight saving needs no second cron) sends to each user with `todoDue.push` on, an `active` feed whose last success is under 26 hours old (stale data mustn't remind), and at least one not-done item with `due_date` = tomorrow. Runs until 23:59 catch up if one fails.
- **At most one a day** is enforced by `notification_deliveries.dedupe_key` = `todo-due:<userId>:<YYYY-MM-DD>` (unique), whatever retries happen.
- **Payload** (`PushPayloadSchema`, V2 §6.4): `{type: "todo-due", title: "3 things due tomorrow", body: "Project 2 (CMSC216) 11:59pm, WebAssign 5 (MATH240) 11:59pm and 1 more", url: "/todo?day=2026-09-29", tag: "todo-due"}`; `TTL` 21600, `Urgency: normal`, `Topic: todo-due`. One item: "Project 2 is due tomorrow" / "CMSC216 · 11:59pm". Titles are cut to 60 characters.
- **The `notification_deliveries.type` CHECK** gains `'todo-due'`. V2 §6.3's `0006_notifications` hasn't landed, so this document adds it there; if 0006 lands first without it, `0011_todo` rebuilds that table with the wider CHECK.
- Push needs the PWA on iOS (V2 §3.3). Turning on the row runs the same permission flow as any channel toggle.

## 5. Security and privacy

### 5.1 The feed link is a secret
- **Never logged**, anywhere: not in `console.*`, not in error messages, not in analytics, not in `notification_deliveries`, not in a URL or query string. It travels in exactly two places: the `todo/connect` POST body, and `crypto.ts` → the fetcher.
- **A worker test** connects a fixture feed, runs a failing and a succeeding fetch, disconnects, and asserts that the token appears in no captured log line, no server analytics event, no API answer, and no D1 column except `url_enc` (checked by scanning every table).
- **A lint rule** in `scripts/check-imports.ts`: only `src/server/todo/crypto.ts` and `fetch.ts` may reference `url_enc` or call the decrypt function.
- **SSRF:** only the two ELMS hosts, re-checked on every redirect (§3.5).
- **CSRF and origin:** every `todo/*` route is a same-origin POST with the origin check (V2 §12).
- **Rendering:** item titles and course labels come from professors and ELMS; they render as plain text. Links render only when they're on the two ELMS hosts, with `rel="noopener noreferrer"`.

### 5.2 Plan data
- The transcript paste never leaves the browser; only the resulting doc is saved (§2.10).
- Grades: §2.5.
- Four-year docs are sync docs: stored like plans, deleted with the account.

### 5.3 `/privacy` updates
Each product PR updates its section of `/privacy` (built by `v2/privacy`), in plain words with contractions:
- **Plan:** "Your four-year plan is saved in your browser. If you're signed in, it's also saved on our server so it's on your other devices. That includes any grades you imported. Nobody else can see your plan or your grades, and we don't use them for anything else. When you paste a transcript, it's read in your browser and never sent to us; only the courses you import are saved."
- **Todo:** "To show your deadlines, we keep your ELMS calendar link on our server, encrypted, and check it about every 20 minutes. We store the assignments and events it lists (titles, courses and due dates) and which ones you've marked done. We don't get your grades, submissions or ELMS password, and we never sign in to ELMS or Gradescope for you. Disconnect any time and we delete the link and everything from it at once."
- The "What we store" table gains the rows `four-year plans`, `ELMS calendar link (encrypted)`, `deadlines from ELMS`, `done marks`.

### 5.4 Copy
Copy follows `SPEC.md` §3.13, now with **contractions everywhere** ("It's supposed to feel a little personal"): "you'll", "it's", "don't", "we'll". Plain words, active voice, specific errors. No sparkles in Plan or Todo (no model output in v3's first release).

## 9. Later

### 9.1 Requirements from the catalog (a sketch, not v3's first release)

The owner's idea: a model reads UMD's prose requirements into code requirements, with "Report a problem", kept up to date by agents researching each major. Degree audit stays UMD's (u.achieve); this would be an unofficial checklist that says so.

- **Source:** the Undergraduate Catalog (academiccatalog.umd.edu, CourseLeaf), about 150 program pages. Each has requirement tables (`sc_courselist`: course rows, hour columns, area headers, "or" rows) and prose rules ("select five 400-level courses from at least three areas, no more than three in one"). A new ingest source, `src/ingest/programs/`, saves each page and extracts tables and prose with golden tests, like every parser.
- **A requirement language** in `src/core/schema/requirements.ts`, small and closed: `all`, `choose {n | credits}`, `course`, `wildcard` (the same `WildcardSchema`), `gen-ed`, and constraints (`maxFrom`, `distinctAreas`, `minLevel`, `notDoubleCounted`). Evaluating it is pure: `evaluateRequirements(spec, doc, index)` → per requirement `met | partly | not-met` with the entries that count.
- **The model** turns tables plus prose into that language, in JSON mode, validated by the schema; anything it can't express stays as the catalog's sentence, shown verbatim and never evaluated. Its output is LLM output, so the checklist carries the sparkles icon and "Read from the catalog by a model. Report a problem."
- **Review before publishing:** each program's spec lands in an admin queue as a diff against the last one; the owner publishes it. Published specs go to an R2 family `requirements/<program>/<catalogYear>.<hash>.json`.
- **Keeping it current:** an agent job per program re-reads the page each catalog year and when "Report a problem" reports pile up, and proposes a new spec to the same queue.
- **UI:** a Requirements tab in Plan, per program and catalog year ("Computer Science B.S., 2026–27"), always with "Unofficial. Your degree audit is the official check."
- **Out even then:** majors' special cases the language can't say (CS areas and concentrations, SOCY research courses) show as the catalog's text until someone models them by hand.
